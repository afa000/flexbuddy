# Task: FB-011 - Ask whether an imported block was worked

Status: Ready for implementation
Risk: high (the chosen status decides whether a block counts toward earnings, hours and net)
Implementer: Claude Code (Opus). The owner handed this task to this session on November 5, 2026.
Review: fresh Claude Code session (Opus), review-task skill

Source: DX-01 in `docs/driver-experience-plan.md`.

## Objective

A screenshot of an accepted block only proves the driver accepted it. Today the import review preselects
"Completed · worked and paid" for every screenshot whose time has passed, and for every screenshot where no date was
read. A driver who taps Add shift without looking saves a block they may never have worked, and its pay counts toward
earnings, hours and net. The word "paid" also claims something no screenshot shows.

The driver should decide, every time, whether they worked the imported block. The app can still suggest an answer.

## Current behavior

- The import review's Status select has two options, Completed (first) and Scheduled. `populatePreview` selects the
  server's `suggestedStatus`, which is Scheduled for a block that hasn't started and Completed otherwise, including
  when no date was read. `resetImport` selects Completed.
- `POST /shifts` with no `status` saves a Completed block. Both current clients always send a status: the import form
  from `#importStatus` and the Add/Edit dialog from `#editStatus` (also when queued offline).
- "Complete this scheduled shift" shows only when the import status is Completed and the server found a matching
  scheduled block.

## Required behavior

1. **No preselected status.** The import Status select starts on an empty, required choice ("Choose one") for every
   screenshot: past, future, or no date read. Choosing a different screenshot, Choose again, Cancel, removing the file
   and a shared screenshot all start from the empty choice again. Saving without a choice is blocked by the form's own
   validation and moves focus to the select.
2. **The suggestion is a hint, not an answer.** Below the select, a hint says what the screenshot suggests:
   - suggested Scheduled: the block hasn't started yet, so it's probably scheduled;
   - suggested Completed with a date read: the block's time has passed; choose Completed only if you worked it;
   - no date read: no date was read, so choose whether you worked it.
   The hint never changes the select. `suggestStatus` stays as it is on the server: it still drives the import
   warnings and duplicate matching.
3. **Clear option wording.** Completed reads as "Completed · I worked this block" and Scheduled as "Scheduled ·
   accepted, not worked yet". Neither option says paid. The hint for a past block says payment is checked later
   against payouts, without adding a paid/unpaid field.
4. **Until a choice is made**, the form behaves as it does for Completed except that it offers no completion shortcut:
   tips and miles are editable, the "Complete this scheduled shift" notice is hidden (`choose` only offers it for
   `COMPLETED`), the already-logged duplicate notice still shows, and the save button reads "Add shift" (or "Add
   anyway" for a duplicate). A future-date warning keeps its current text.
5. **Server: no silent Completed.** `ShiftService.createShift` rejects a request with no status with a 400 and a new
   localized message (`error.shift.statusRequired`), and saves nothing. Backup restore keeps its own status parsing and
   is unaffected. A request id replay of an earlier create still returns the saved shift.

### Compatibility

- Current import and Add/Edit clients always send a status, so they keep working.
- Writes already queued offline by an older cached script also carry a status (both old forms sent one), so the outbox
  replays them unchanged.
- An older cached script that still preselects Completed keeps doing so until the service worker updates it; the server
  can't tell that choice from a deliberate one. The script change ships with a new `BUILD_ID` like every release.
- A third-party or hand-written API call with no status now gets a 400 instead of a Completed block. No such client is
  known; record this in the README's API notes.

## Out of scope

- How earnings, hours or net are calculated, and the status model (no new paid/unpaid field). Payment tracking is
  DX-12.
- Existing saved shifts: nothing is reclassified.
- The Add/Edit dialog's status select, editing completed blocks back to scheduled (DX-02), multi-file import (DX-10).
- OCR, warnings and duplicate matching on the server.

## Acceptance criteria

- [ ] Past, future and no-date screenshots all open the review with no status chosen and the matching hint; choosing a
      different screenshot, Choose again, Cancel or a shared screenshot resets the choice.
- [ ] Add shift without a choice saves nothing and focuses the Status select.
- [ ] Choosing Scheduled saves a block with no earned pay, hours or net (tips/miles cleared as today); choosing
      Completed saves a worked block.
- [ ] Cancel, navigating away, OCR failure and a duplicate warning create no record.
- [ ] "Complete this scheduled shift" appears only after the driver chooses Completed.
- [ ] `POST /shifts` with no status returns 400 with the localized message and saves nothing; with a status it behaves
      as before. Backup restore is unchanged.
- [ ] English and Spanish catalogs have the new and changed keys in the same group; no option or hint says the block
      was paid.

## Security and regression risks

- Earnings: a Scheduled import must stay out of earnings, hours and net; nothing about calculation changes.
- Per-user data: no new query; `createShift` keeps its owner lookup.
- Offline queue and request-id replay must still work for status-bearing requests.
- Backup/restore must not start requiring a status in `CreateShiftRequest` validation.
- Both language catalogs.
