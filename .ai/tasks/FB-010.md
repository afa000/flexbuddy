# Task: FB-010 - Use the IRS mileage rate for each block's date

Status: Ready for implementation
Risk: high (earnings and tax figures, a data migration, backup/restore)
Implementer: Claude Code (Sonnet)
Review: fresh Claude Code session (Opus), review-task skill

## Objective

FlexBuddy's standard-mileage default is still the 2025 IRS rate, $0.70 a mile. For 2026 the IRS set
[72.5 cents](https://www.irs.gov/newsroom/irs-sets-2026-business-standard-mileage-rate-at-725-cents-per-mile-up-25-cents)
and raised it to 76 cents for travel from July 1, 2026 (Announcement 2026-11). Every driver on the default
underestimates vehicle cost, so estimated net, set-aside and the year summary they give a tax preparer are all off. A
single rate can't be right for 2026 at all, and many drivers can't get the default anyway: saving the Vehicle costs form
stores the $0.70 shown in it as their own rate.

The default should be the IRS rate in effect on each block's date. Saving the form should no longer pin the default,
and accounts already pinned to $0.70 by that form should go back to the default. The owner approved that last point on
October 30, 2026.

## Current behavior

Checked against `main` at 5b45efe.

- `effectiveMileageRate` returns the account's `mileage_rate` or, if it's null, the configured default of 0.70
  (labelled 2025). The same rate applies to every block, whatever its date.
- `NetEarningsCalculator` multiplies total miles by that one rate.
- **Account > Vehicle costs:** the rate field shows the effective rate. **Save settings** sends `mileageRate:
  Number(field)`, so a driver who only changed the method, or saved without touching anything, now has 0.700 stored.
  They no longer follow the default. Only **Use app default** sends `null`.
- **Tax summary:** the header says "Standard mileage at $0.70/mile", and every month row and the CSV show 0.70.
- **Backups:** they write the stored rate, so a backup made after saving the form contains "0.70" (or "0.700"), and
  restoring it pins the rate again.
- 0.70 is the only default the app has ever had (`git log -G mileage -- application.properties`).

## Required behavior

1. **A dated table of IRS business rates.** Add one class, for example `service/IrsMileageRates`, with a Javadoc saying
   to add a line when the IRS announces a rate. It holds these entries:

   | From | Rate |
   |---|---|
   | 2024-01-01 | 0.670 |
   | 2025-01-01 | 0.700 |
   | 2026-01-01 | 0.725 |
   | 2026-07-01 | 0.760 |

   `rateOn(LocalDate)` returns the latest entry on or before the date. Dates before 2024 use 0.670. Remove the
   `flexbuddy.mileage.default-rate` and `default-rate-year` properties and their `@Value`s. The rate is no longer
   configured per environment.
2. **Rate per block.** If the account has its own rate, it applies to every block, as today. Otherwise each block uses
   `rateOn(block date)`. Give the calculator a rate source in place of a single `BigDecimal`. A small record or interface
   with `rateOn(LocalDate)`, built from the account settings, is enough; name it as you like. Then:
   - mileage cost is the sum of each block's counted miles times its rate, rounded to cents once at the end;
   - for a range with one rate, every result must equal today's to the cent;
   - expenses, actual-expenses mode and everything else in the result are unchanged.
3. **Callers.** Every caller listed above uses the rate source. The block evaluator uses the rate for the block being
   evaluated, which is today.
4. **Settings response.**
   - `mileageRate` is the rate in effect today: the account's own rate, or today's IRS rate.
   - `defaultMileageRate` is today's IRS rate.
   - Replace `mileageRateYear` with `defaultMileageRateSince` (the `LocalDate` of today's entry).
   - Add `customMileageRate` (`true` when the account has its own rate).
   - Keep the extra constructors compiling or remove the unused ones.
5. **Account page.**
   - Replace `js.account.mileageRateHelp` with a new key `js.account.irsRateHelp`, and remove the old key from both
     catalogs. Its text is "IRS rate: ${0} per mile since {1}. FlexBuddy uses the rate for each block's date. This is an
     estimate, not tax advice." `{1}` is the date in the driver's language, for example "Jul 1, 2026".
   - Change the Spanish text of `costs.useAppDefault` to "Usar la tarifa del IRS", and English to "Use the IRS rate".
6. **The form stops pinning the default.** On **Save settings**, if the account has no custom rate and the driver
   didn't change the rate field from what was rendered, send `mileageRate: null`. If they typed a different number, send
   it; that's a custom rate. An account that already has a custom rate keeps sending its value, as today.
7. **Migration `V28`.** Reset rates pinned by the old form:
   `update app_users set mileage_rate = null where mileage_rate = 0.700;`. Start the file with a comment saying why: the
   form stored the displayed default, and 0.70 was the only default ever shipped. This is the owner's decision. A driver
   who really wanted 0.70 can set it again.
8. **Restore.** For the same reason, restoring a backup whose `mileageRate` is numerically 0.70 ("0.7", "0.70" or
   "0.700") sets the account's rate to `null`. Any other rate restores as it is. Older backups stay restorable, and the
   validation at lines 373-377 is unchanged.
9. **Tax summary and CSV.**
   - Each month row's `mileage_rate` is the rate used for that month's blocks. IRS changes take effect on the 1st, so a
     month has one rate.
   - If a row (for example the year total) used more than one rate, show the rate cell empty in the page and the CSV.
     The cost stays exact.
   - The header says "Vehicle costs: Standard mileage at ${0}/mile" when one rate applied to the whole year. Otherwise
     it uses a new key `taxSummary.vehicleCostsStandardMileageIrs`: "Vehicle costs: Standard mileage at the IRS rate for
     each block's date" / "Costos del vehículo: millaje estándar con la tarifa del IRS de la fecha de cada bloque".
   - A custom rate always gives the single-rate line.

## Out of scope

- The medical, moving and charitable rates.
- Custom rates that change by date. A custom rate stays one number.
- How miles are recorded, and the missing-miles messages in FB-009.
- Changing any production value by hand or through Render. The migration runs on deploy like any other.

## Security and regression risks

- **Tax and earnings figures change for every driver on the default.** That's the point, but no figure may change for
  2025 blocks, custom-rate accounts, or the actual-expenses method. The tests above must prove it.
- **Migration:** a single `update` scoped to the exact value 0.700. It never deletes data. It can't be undone per
  account, which is why it is limited to the one value the form stored.
- **Backup/restore:** older backup versions must still restore. The 0.70 mapping applies to every version.
- **Per-user data:** the rate source comes from the signed-in account's settings only.
- **Catalogs:** one key replaced, one added, one changed in both files, with `{0}` and `{1}` kept in Spanish.
- **Sign-in and Android:** untouched.
