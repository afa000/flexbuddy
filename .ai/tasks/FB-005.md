- `flexbuddy.api.enabled=${FLEXBUDDY_API_ENABLED:false}` is off by default.
  Only when true are the API security chain, bearer filter, controllers, services
  and cleanup registered. While off, a narrowly matched rejection in the web chain
  returns 404 for every `/api/v1/**` method before CSRF/session handling. All other
  web paths retain their existing behavior. Tables exist even while off.
- Password reset and account deletion revoke credentials even while the API is off.
- Password authentication does not clear the shared email lock until every required
  code has succeeded. Wrong credentials count once in both shared login buckets;
  wrong codes count once against the email bucket. IP locks are not cleared.
- Serialize credential issuance, code consumption and revocation per account to
  prevent replay and reset races. Re-check challenge expiry after acquiring locks.
- If an unverified account also has two-factor enabled, email verification advances
  to a two-factor challenge; it never bypasses the second factor.
- A new password sign-in retires earlier pending app challenges for that account.
  App-code challenges cannot resend an email (400 `invalid`). Limited email sends
  return 429 with a retry duration. No extra cancellation endpoint is added.
- Sliding expiry is persisted at most hourly; the stored deadline is authoritative
  (up to one hour shorter than an exact 30 days since the latest request).
- Malformed JSON and invalid fields return 400 `invalid`; credentials are bounded,
  never echoed. Authentication writes do not use Idempotency-Key: replaying a code
  fails and sign-out is idempotent only while its token is valid.
- Update docs/api-v1.md with concrete requests, responses and availability.
- Run a fresh read-only security review after verification (owner authorized).
- Shared browser/API code verification and email-code replacement must acquire the
  same account lock; refresh cached TOTP replay state after waiting for that lock.
  Defer browser password-success clearing until final sign-in too. These internal
  security fixes preserve the website's routes, pages and cookie behavior while
  preventing cross-channel replay and failure-count resets.

## Objective

The planned native Android app (Kotlin and Jetpack Compose, replacing the Trusted Web Activity in `android/` once it's
ready) cannot use the website's sign-in. The website signs drivers in with a form,
a session cookie and a remember-me cookie, protected by a CSRF token. A native app needs to sign in with a request, get
a token back, and send that token with every request.

This task adds that, and nothing a driver can see. It is the first piece every later native-app task depends on, and it
ships to production on its own: the new endpoints sit unused until the app exists, and the website must behave exactly
as it does today.

## Current behavior

Checked against `origin/main` at 2091872.

- **One security chain for everything.** `config/SecurityConfig.java` builds a single `SecurityFilterChain`: form
  sign-in at `POST /login`, an optional Google sign-in (`oauth2Login`), remember-me through
  `RotationTolerantRememberMeServices` (cookie `FLEXBUDDY_REMEMBER_ME`, 30 days, stored in `persistent_logins`), and
  CSRF on every POST except `/share-import`. Every JSON endpoint (`/shifts`, `/expenses`, `/account/...`) gets its user
  from `Principal.getName()`, which is the account's email.
- **After the password.** `security/VerifiedLoginSuccessHandler` undoes the sign-in when the account's email isn't
  verified or two-step sign-in is on, keeps the pending user in the HTTP session, and redirects to `/verify-email` or
  `/sign-in/code`. `controller/TwoFactorController` checks the code with `TwoFactorService.verifySignIn` (app code,
  emailed code or recovery code) within a 10-minute pending window, and `security/SignInCompleter` finishes the
  sign-in. Email verification works the same way through `EmailVerificationService.startVerification` and `verify`.
- **Locks.** `security/AttemptLimiter` holds the locks. `security/LoginAttemptFilter` refuses `POST /login` while
  bucket `login-email` (by email) or `login-ip` (by connection) is locked, before the password is checked.
  `security/LoginAttemptEvents` records failures and clears them on success from Spring's authentication events.
  Wrong second-step codes count against the same `login-email` bucket. `security/ClientAddressFilter`, registered as
  a servlet filter for every request, makes `getRemoteAddr()` the driver's address behind Render's proxy.
- **Signing devices out.** `PasswordResetService.resetPassword` and `AccountService.deleteAccountData` remove the
  account's remember-me tokens with `persistentTokenRepository.removeUserTokens(email)`. There is no change-password
  feature; a reset is how a password changes.
- **Accounts without a password.** Drivers who signed up with Google have `passwordSet = false` and can't sign in with
  a password until they set one through the reset email.
- **Tokens elsewhere.** Password reset links are stored as SHA-256 hashes (`PasswordResetService.hash`). The newest
  migration is `V27__language.sql`. The app has no JWT or OAuth resource-server dependency, and this task must not add
  one.

## Required behavior

### 1. Device tokens

- A new migration `V29__app_tokens.sql` adds two tables:
  - `app_token`: `id`, `owner_id` (references `app_user`), `token_hash` (unique, the SHA-256 of the token),
    `device_name` (up to 80 characters, nullable), `created_at`, `last_used_at`, `expires_at`.
  - `app_sign_in_challenge`: `id`, `owner_id`, `challenge_hash` (unique), `purpose` (`VERIFY_EMAIL` or `TWO_FACTOR`),
    `device_name`, `created_at`, `expires_at`.
- A token is 32 bytes from `SecureRandom`, base64url without padding, prefixed `fbt_` so it's recognisable if it ever
  leaks into a log. Only its hash is stored. The plain token is returned once, at sign-in, and never logged.
- A token is valid until 30 days after it was last used (the same 30 days as remember-me). Each use moves `expires_at`
  forward, but `last_used_at` and `expires_at` are written at most once an hour per token, so normal use doesn't write
  to the database on every request.
- A challenge is 32 random bytes, stored hashed, and expires 10 minutes after it was made (the same window as the
  browser's pending sign-in). It is single-use and deleted when the sign-in completes or is abandoned.
- Expired tokens and challenges are deleted by a daily cleanup. Add it to an existing scheduled job's class or a new
  one, following how `PasswordResetService` purges expired links.

### 2. A separate, stateless security chain for `/api/v1/**`

- Add a second `SecurityFilterChain` with `securityMatcher("/api/v1/**")` and a higher priority (`@Order`) than the
  existing one, which stays exactly as it is for every other path.
- The new chain:
  - never creates or reads an HTTP session (`SessionCreationPolicy.STATELESS`) and has no form sign-in, OAuth sign-in,
    remember-me or logout;
  - ignores the session and remember-me cookies, so a browser's cookies can never authenticate an `/api/v1` request;
  - has CSRF turned off, which is safe only because nothing on it is authenticated by a cookie;
  - permits `POST /api/v1/auth/sign-in`, `/api/v1/auth/code` and `/api/v1/auth/code/resend` without a token, and
    requires a token for everything else under `/api/v1`;
  - answers a missing, unknown or expired token with `401` and a JSON body `{"error": "unauthorized"}`, never a redirect
    to `/login`.
- A bearer-token filter reads `Authorization: Bearer <token>`, looks up the hash, rejects an expired token, and sets an
  authentication built from the same `UserDetailsService` the website uses, so `Principal.getName()` is the account's
  email and every existing service works unchanged.

### 3. Endpoints

All take and return JSON. Errors are codes, not sentences; the app shows its own text in the driver's language, so no
catalog keys are needed.

- **`POST /api/v1/auth/sign-in`** with `{"email", "password", "deviceName"}`:
  - While `login-email` or `login-ip` is locked: `429` with `{"error": "locked", "retryAfterMinutes": n}`, before the
    password is checked, as `LoginAttemptFilter` does.
  - Wrong email or password, or an account without a password: `401` with `{"error": "invalid_credentials"}`. The same
    answer either way, so the endpoint doesn't reveal which emails have accounts. The failure counts against both lock
    buckets exactly as a failed form sign-in does. Authenticating through Spring's `AuthenticationManager` with
    `WebAuthenticationDetails` gets this from `LoginAttemptEvents` for free.
  - Right password, verified account, two-step off: `200` with `{"status": "signed_in", "token", "expiresAt",
    "account"}`.
  - Right password, email not verified: start verification with `EmailVerificationService.startVerification` and answer
    `200` with `{"status": "code_required", "purpose": "verify_email", "challenge", "expiresAt"}`.
  - Right password, two-step on: send the emailed code if the method is `EMAIL` (as `VerifiedLoginSuccessHandler`
    does), then answer `200` with `{"status": "code_required", "purpose": "two_factor", "method": "app" | "email",
    "challenge", "expiresAt"}`.
- **`POST /api/v1/auth/code`** with `{"challenge", "code"}`:
  - Unknown, used or expired challenge: `401` with `{"error": "challenge_expired"}`.
  - Wrong code: `400` with `{"error": "code_wrong"}`, or `{"error": "code_expired"}` when the emailed code itself has
    expired, counted against `login-email` as the browser does. Once that lock holds, delete the challenge and answer
    `429` locked.
  - Right code: delete the challenge and answer like a successful sign-in. A recovery code also adds
    `"recoveryCodeUsed": true`, as the browser's `?recovery-used` does. Verification uses
    `EmailVerificationService.verify`; two-step uses `TwoFactorService.verifySignIn`.
- **`POST /api/v1/auth/code/resend`** with `{"challenge"}`: sends a new emailed code for that challenge, with the same
  limits as the browser's resend; `204`, or `429` when the email code limits refuse.
- **`POST /api/v1/auth/sign-out`** (token required): deletes the token that made the request; `204`.
- **`GET /api/v1/account`** (token required): `{"email", "displayName", "language", "timeZone", "emailVerified",
  "twoFactorMethod"}` for the signed-in driver only. This is the endpoint the app calls to check its token, and the
  one the tests use to prove the chain works.

The `account` object in a sign-in answer is the same shape as `GET /api/v1/account`.

### 4. Signing devices out

- `PasswordResetService.resetPassword` also deletes every app token and challenge for the account, next to
  `removeUserTokens`. A password reset signs out every phone, as it already signs out every browser.
- `AccountService.deleteAccountData` deletes the account's app tokens and challenges before the account itself.
- Tokens and challenges are not part of backups, like remember-me tokens. Backup and restore don't change.

## Out of scope

- Any change to the website's sign-in, pages, cookies, CSRF or the existing JSON endpoints.
- Google sign-in from the native app. Verifying a Google ID token sent by the app needs a new dependency (Spring's
  OAuth2 resource server or Google's client library) and the owner's approval; it gets its own task.
- Creating an account from the app. The app can open the website's sign-up page until a later task.
- Exposing shifts, expenses, reports or anything else under `/api/v1`. Each gets its own task, built on this one.
- A "signed-in phones" list in Account, refresh tokens, and push notifications to the app.
- The Android projects in `android/`.

- [ ] `/api/v1/**` has its own stateless chain. Every other path behaves exactly as before, and the existing test suite

- [ ] Sign-in returns a token for a verified account without two-step sign-in, and a challenge for an unverified
      account or one with two-step sign-in (app or email method).
- [ ] A challenge plus the right code returns a token; a recovery code works and is reported.
- [ ] Wrong passwords and wrong codes lock the email and connection exactly as the website does, and a lock refuses
      sign-in before the password is checked.
- [ ] `GET /api/v1/account` works with a valid token and returns `401` JSON (no redirect) with no token, an unknown
      token, an expired token, a signed-out token, or only the website's session or remember-me cookie.
- [ ] Only token hashes are stored, and no token or `Authorization` header appears in logs or error alert emails.
- [ ] A password reset and account deletion remove the account's app tokens.
- [ ] Tokens slide to 30 days after last use, with at most one database write per token per hour.

## Security and regression risks

- **Sign-in is the riskiest code in the app.** The website's chain must not change. A second chain with the wrong
  matcher or order could open or break every page; the regression tests above guard it.
- **CSRF.** Turning CSRF off is only safe because the `/api/v1` chain never accepts cookies. Test that a session or
  remember-me cookie alone gets `401`.
- **Locks.** The API must share the website's lock buckets, or it becomes a way around them. Check locks before the
  password, and count wrong codes.
- **Account enumeration.** Wrong email, wrong password and password-less accounts get the same answer.
- **Token storage.** Hashes only, a 256-bit random secret, constant-time-safe lookup by hash, never logged. The error alert
  emails in `alert/` don't read request headers today; keep it that way.
- **Per-user data.** The token decides the account; no request body or path parameter can choose another account.
- **Database.** One new migration with foreign keys to `app_user`. Account deletion must delete the new rows first, or
  it will fail on the foreign key.
- **Backups, earnings rules, both catalogs and Android:** untouched.
