# Task: FB-050 - Expose the annual tax summary to Android

Status: Ready for implementation
Risk: high (tax estimates and account isolation)
Implementer: Codex (Astra or Sol at High or above)

## Objective

Give the native app the server-calculated figures for a selected tax year so it can show the last synced
summary offline. This is the server dependency for the tax portion of NA-13 step 2 and part of NA-08.
Android earnings reports can calculate from the complete synced blocks and expenses independently.

## Current behavior

The website's GET /tax/summary returns the selected year's estimated reserve and recorded payments
through TaxService.summary. It uses the account's local year by default. The printable tax report
and CSV use separate website endpoints. API v1 has no annual tax summary.

## Required behavior

- Add GET /api/v1/tax/summary with the existing API enablement and bearer-token security. Use only the
  authenticated account for the year default, settings, and calculation. An omitted year defaults to the
  account-zone year via UserTimeService. Accept integer years 2000 through 2100 inclusive, using the existing
  service bounds. A malformed or out-of-range year returns the API's JSON 400 invalid response for year.
- Call TaxService.summary for all figures. Preserve the website's selected-year, current-week,
  expense, payment, reserve, and due-date semantics. The payload includes year, percent, netYearToDate,
  reserveToDate, paid, remaining, thisWeekNet, thisWeekSetAside, nextDueDate, and quarters. Each of the four
  quarters includes quarter, from, to, dueDate, net, setAside and paid, in service order. Return annual
  and quarterly paid totals without individual payment records or notes. No printable report data is needed.
- Encode money as two-decimal strings, the percentage as a decimal string, and dates as ISO local dates.
  Keep nulls from the service for unset estimates and a missing next due date. Document that the reserve
  and set-aside are estimates based on the driver's configured percentage.
- Use ApiEtags for private conditional reads. An authorized matching If-None-Match returns 304 with no body.
  A changed representation returns 200 with the new ETag. The phone will record when it successfully
  fetches or revalidates each account and year's summary. Document the endpoint, field meanings and nulls,
  status codes, and conditional behavior in docs/api-v1.md.

## Out of scope

Android code and cache, earnings Reports and Standing endpoints, tax settings and payment writes,
printable summaries, CSV, changes to tax calculations or the website, migrations, dependencies and
production flag changes.

## Acceptance criteria

- [ ] The API and website agree for equivalent made-up accounts and dates, including a recorded payment,
      a saved zero percentage, an unset percentage, and a year whose final due date has passed.
- [ ] Explicit historical years work, both supported bounds are accepted, and invalid year input gets
      JSON 400. An omitted year follows the account's zone across New Year's midnight.
- [ ] The payload uses the API's decimal and date encodings and contains the four quarters, annual
      and quarterly payment totals, and only the specified fields.
- [ ] Missing or invalid tokens and web-session-only requests receive 401 with the API enabled.
      With the flag off the route is 404. Two accounts with different settings, figures and payments
      see only their own data, including when sending the other account's validator.
- [ ] Unchanged data revalidates with 304 and an empty body. A change affecting the summary returns
      200 with a new ETag. Both responses have Cache-Control: private, no-cache.

## Security and regression risks

The endpoint returns private tax figures. Authenticate before calculating or processing a validator,
scope every read to the principal, and keep private HTTP cache semantics. Do not log tokens, raw
payment data or tax figures. Reuse the website's service so native tax estimates follow the same rules.
