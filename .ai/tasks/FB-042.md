## Objective

Let the native app obtain the driver's actual calculation settings, rather than trying to infer them from
Home's computed totals. Android FB-041 (PR afa000/flexbuddy-android#11, merged November 17, 2026) pins shared
library 0.2.0 and proves its figures on API 26/37. The app already caches blocks and expenses, but lacks the
complete inputs needed to reproduce figures offline. This server task supplies those settings through a
read-only authenticated API; offline app integration follows in a separate task.

Source: docs/native-app-plan.md NA-13 step 2 and the FB-041 follow-up boundary.

## Current behavior

GET /api/v1/account exposes identity/language/time zone only. GET /api/v1/home returns computed figures and goal
progress, not the settings required to recompute them. AccountSettingsService already supplies defaulted vehicle
method, effective/current mileage rate, whether that rate is custom, goal amounts/basis and payout schedule to
the website. Its full response also contains a private calendar feed path and other unrelated settings and must
not be returned as the native API response.

## Required behavior

- Add GET /api/v1/calculation-settings, requiring the existing bearer-token authentication and enabled only with
  FLEXBUDDY_API_ENABLED, following the existing conditional API controller conventions. No caller-supplied account
  email/id parameter; resolve the owner from Principal as existing endpoints do.
- Return a dedicated API DTO with exactly these eight fields (example uses made-up settings):

  ```json
  {
    "timeZone": "America/New_York",
    "vehicleCostMethod": "standard_mileage",
    "customMileageRate": null,
    "weeklyGoal": "600.00",
    "monthlyGoal": null,
    "goalBasis": "gross",
    "payoutDays": ["tuesday", "friday"],
    "payoutLagDays": 1
  }
  ```

- Map the existing AccountSettingsService result, preserving its defaults and existing rules. No entity
  serialization or change to the website's AccountSettingsResponse shape. Enum codes use ApiValues.code, goals
  use ApiValues.money, and a custom mileage rate uses ApiValues.decimal without rounding to two places.
- customMileageRate is a nullable decimal string: null when AccountSettingsResponse.customMileageRate() is false,
  otherwise its mileageRate() value. An explicit zero custom rate remains "0...", not null. IRS mode must never
  send today's effective IRS rate as a custom rate. The shared library supplies dated IRS rates; no table copy,
  current-rate field, tax estimate or new arithmetic in this endpoint.
- timeZone, method, goals, basis, payout days and lag follow the existing settings service's returned values/defaults.
  Do not change existing invalid/legacy settings behavior in this task. Document time-zone fallback to the same
  AppUser.DEFAULT_TIME_ZONE used by UserTimeService if a consumer encounters a missing/invalid zone.
- payoutDays is sorted Monday through Sunday with lowercase English codes, independent of JVM locale and stored
  input ordering. Preserve PayPeriodCalculator's existing default parsing; don't introduce a second parser.
- Use ApiEtags.withEtag with the dedicated DTO: strong content ETag, private/no-cache, 304 with no body for a
  matching If-None-Match, and 200 with a new tag when a represented setting changes. Stable byte ordering is
  required. Do not add a clock timestamp, pretend updatedAt, cursor, migration or settings revision just to track
  freshness. An unchanged response should remain revalidatable across midnight.
- Freshness contract: a client stores the settings body, ETag and its own successful-check time per account;
  either 200 or 304 refreshes that check time. A changed tag requires recalculation even when block/expense cursors
  are unchanged. Settings, block and expense responses are independent reads, not a claimed atomic sync snapshot;
  later Android integration must coordinate refreshes and show the oldest relevant successful-check time.
- Keep GET read-only. Reading must not mint/regenerate calendar tokens, save settings or change database rows.
  Authentication applies before returning 304. Existing auth errors, methods and API-disabled behavior remain.
- Add docs/api-v1.md for the route, exact fields/nullability/default source, lowercase codes, rate precision,
  timezone semantics, conditional requests and freshness limitations. Update docs/native-app-plan.md NA-13 to
  identify this prerequisite and keep app integration explicitly pending.

## Security and regression risks

Never serialize the full website settings DTO: its private feed link is not part of this API. Preserve token-only
per-account authorization and feature-switch behavior. A mistaken custom/IRS distinction or rate rounding would
silently corrupt offline figures; verify both explicitly. Do not touch production settings, credentials or data.
