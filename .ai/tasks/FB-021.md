## Objective

A driver who accepted a week of blocks, or worked several, has to import them one screenshot at a time: pick, wait,
review, save, go back to the + button, pick again. Let them pick several screenshots at once and review each in turn,
without any risk of a block being saved twice or saved without a review.

## Current behavior

The file input takes one file, and a drop uses only the first file. `POST /shifts` from the import form is sent
without an `Idempotency-Key`, so a save whose answer is lost and is tried again adds a second block. The duplicate
notices come from the server's preview, which only knows about blocks saved before that screenshot was read.

## Required behavior

1. **Picking.** The file input takes several files (`multiple`), and a drop uses every file. One file keeps today's
   single-screenshot flow exactly. Two to ten files start a batch. More than ten are refused with "Choose up to 10
   screenshots at a time." and nothing starts. The import card says "You can choose up to 10 at once."
2. **Queue.** A batch shows a list in Step 1, one row per file in the order picked, each with its state:
   waiting, reading, ready to review, reviewing now, couldn't be read (with the reason), same screenshot as an earlier
   one, added, completed the scheduled block, skipped, or not imported (stopped). A heading says "Screenshot 2 of 5"
   for the one under review. Every file always has a visible row; one bad file never removes the others.
3. **Checks before reading.** A file that isn't PNG/JPEG or is over 5 MB gets its reason on its row and is never sent.
   A file with the same bytes as an earlier file in the batch (SHA-256, falling back to name + size + modified time)
   is marked "Same screenshot as #N" and is not read.
4. **Reading.** Files are read one at a time, in order, through the existing `POST /shifts/import-preview` (so the
   server read gate and limits are unchanged). The first ready file opens in Step 2 while later files are read.
   A screenshot the server can't read (400) shows the server's reason and reading continues. A busy server (503), a
   timeout or a lost connection marks that file "Couldn't be read" with Try again, and pauses reading; the rest stay
   waiting until the driver taps Continue reading. Nothing is read or retried while offline without a tap.
5. **Reviewing.** Step 2 is the existing review form, filled from the current file, with the explicit status choice
   of FB-011. Saving adds the block and opens the next ready file; Skip this screenshot moves on without saving. A
   ready row's Review button opens that file instead. Nothing is ever saved without the driver pressing a save
   button on that file's review.
6. **No double saves.** Each file gets its own request id when the batch starts, sent as `Idempotency-Key` on its
   `POST /shifts` and (a separate id) on its "Complete this scheduled shift" `PATCH`. A double tap, a retry after a
   lost answer, or a 409 DUPLICATE is answered with the first save, never a second block. If the replayed block has
   different values than the form now holds (the first save landed before the driver edited), the driver is told
   and offered Open it. The single-screenshot flow sends a request id too.
7. **Duplicates within the batch.** The server's notices still show (FB-008). They can't know about blocks this
   batch saved after the file was read, so the review also checks the blocks saved earlier in this batch, with the
   server's rule (same day, overlap of 30 minutes or more, station equal or containing the other):
   - saved as scheduled and this file is marked Completed: "Screenshot N in this batch added this block as
     scheduled." with Complete this scheduled shift, which completes that block with the pay on this file;
   - otherwise: "Screenshot N in this batch already added this block." with Open it, and the save button says Add
     anyway.
   The batch check uses the form's current values and replaces the server's notice when both apply.
8. **Stopping and finishing.** Stop importing aborts the current read, marks every unsaved file "Not imported", and
   keeps the saved ones listed with Open. When no file is left to read or review, the heading says "Added 3 of 5
   screenshots." and Done clears the batch and goes Home. History and totals refresh after each save.
9. **Leaving.** Switching screens inside the app keeps the batch. Reloading or closing the page while files are
   still unsaved asks the browser's leave-page question; the batch isn't kept after a reload (OCR is online-only and
   no draft is stored).

## Out of scope

- Server-side changes: no new endpoint, no persistence or migration, no change to OCR, the read gate or its limits.
- Android share target and sharing several images (DX-11).
- Reading files in parallel.

## Acceptance criteria

- [ ] Every file has a visible result and an explicit review/completion decision; an invalid file does not discard
      other reviews.
- [ ] Duplicates are checked against saved history (server) and earlier saves in the same batch; a retry or double
      tap cannot create the same reviewed entry twice.
- [ ] Partial success shows exactly what saved; stopping ends further work and leaves saved records intact and
      listed.
- [ ] Navigating or losing the connection never saves or retries an unreviewed file by itself.
- [ ] Node tests cover mixed valid/invalid files, repeated images, a changed pay on a block saved earlier in the
      batch, a preview read before an earlier save (stale server matches), server-busy responses and a save
      interrupted then retried. Java tests cover the request-id replay that the batch relies on.
- [ ] English and Spanish; phone width.

## Validation

- Browser, local test account, synthetic screenshots from the test resources: a batch of mixed files at 390px with the

  can only be simulated (offline toggle); a real phone's multi-select picker is not checked.

## Security and regression risks

- Earnings: every save still goes through `POST /shifts` / `PATCH status` with the driver's explicit status; scheduled
  blocks count for nothing until confirmed. The single-screenshot flow must behave as before.
- Per-user data: request ids are looked up per owner by the existing service; nothing new reaches the server.
- Memory: the browser holds at most ten files of 5 MB; the server still reads one at a time.
- Both catalogs; `sw.js` lists the new script.
