# Task: FB-033 - Read-only blocks and Home for the native app, with change-only sync

Status: Ready for implementation
Risk: high (a migration, earnings figures in a new API, and a sync design that must never leave a deleted block on a
driver's phone)
Implementer: Claude Code (Opus)
Review: fresh Claude Code (Opus), Codex (Sol) or Antigravity (Gemini 4 Argon) session, review-task skill

Plan section: NA-04 in docs/native-app-plan.md, server half. The app half (Home screen and Room cache) is a later task in
`flexbuddy-android` that names this one. Builds on FB-005 (token sign-in) and runs on the FB-032 test server.

## Objective

The native app can sign in, but it has nothing to show. Drivers open FlexBuddy mostly to look at this week: their
blocks, what they earned, their net per hour and whether any block is missing miles. This task gives the app read-only
access to the driver's blocks and to the Home figures, computed by the same services the website uses, so the two
never disagree.

It also settles how the app keeps its copy current. A phone that reloads every block on every open wastes drivers'
data and the free database's compute hours. Every list endpoint from now on returns only what changed since the
phone's last sync, plus the blocks that were deleted, and answers `304` with no body when nothing changed (the "Sync"
decision in the plan). This task defines that pattern on blocks, so later endpoints copy it.

## Current behavior

- `/api/v1` has only sign-in, codes, sign-out and `GET /api/v1/account` (FB-005). With `FLEXBUDDY_API_ENABLED` unset,
  every `/api/v1` path answers 404.
- The website reads blocks with session-authenticated JSON: `GET /shifts` (filters and sort), `GET /shifts/{id}`,
  `GET /shifts/statistics`, `GET /shifts/goals`, `GET /shifts/missing-miles`. Money there is a JSON number.
- Home works out "this week" in the browser (Monday to Sunday in the device's time) and asks for statistics for that
  week and the last seven days, plus the block list.
- `Shift` has `createdAt` and `updatedAt`, set by `TimestampListener` on JPA saves. Deleting puts a block in Recently
  deleted (`deleted_at`, `delete_batch`) and restoring clears it. **These are native `update` queries
  (`softDelete`, `softDeleteAll`, `restoreDeleted`, `restoreBatch`), so they bypass the listener and leave
  `updated_at` unchanged.**
- Rows are removed for good by: permanent delete and empty trash (Recently deleted only), the daily purge after 30 days,
  undoing a backup restore (`deleteBatch`, which removes rows that were live), and account deletion.
- The website reads `updatedAt`: it shows "last edited" when it is more than a minute after `createdAt`
  (`app.js` around lines 1348 and 2626), and sends it back as `expectedUpdatedAt` to detect conflicting edits
  (`app.js` 1771, `finish.js` 222, `outbox.js` 389). So its meaning must not change.
- Nothing records when a block was deleted or restored in a way a sync can query, and there is no index for it.

## Required behavior

### 1. A sync time on every block

`updated_at` keeps its meaning for the website. Sync uses its own column, so deleting or restoring a block doesn't make
it look edited or break an offline edit's conflict check.

- `V30__sync.sql` (one new migration; no committed migration changes):
  - adds `shift.sync_changed_at`, a timestamp, filled for existing rows with the later of `updated_at` and
    `deleted_at`, then made not null
  - adds a nullable `sync_reset_at` timestamp column to `app_users`
  - adds an index on `shift(owner_id, sync_changed_at)`. Declare the column and index on `Shift` too, as the existing
    indexes are, so `ddl-auto=validate` and the PostgreSQL migration test both agree.
- `sync_changed_at` moves on every change to a block: set with `created_at`/`updated_at` on JPA saves (in
  `TimestampListener` or a `Shift` callback, whichever keeps `Timestamped` unchanged for other entities), and set by
  the native queries `softDelete`, `softDeleteAll`, `restoreDeleted` and `restoreBatch` to the instant they write.
  Search for every other `update shift` in the code and do the same.
- Blocks inserted by a backup restore get `sync_changed_at` set to the time of the restore, whatever times the backup
  file carries.

### 2. Reset when a deletion can't be reported

Some removals leave nothing behind to report. Instead of a tombstone table, the account records when that happened and
any phone that synced before it reloads everything once.

- `sync_reset_at` is set to the current instant whenever any of these removes or replaces this account's blocks:
  permanent delete, empty trash, undoing a restore (`deleteBatch`), and a backup restore (in either mode). It is set in
  the same transaction as the change.
- The daily purge does not set it. Instead, a cursor older than the purge window (30 days) always gets a full answer.
  Use a margin so a cursor from 29 days and 23 hours ago can't race the purge: anything older than 29 days is full.
- Account deletion doesn't need it: FB-005 already revokes every token.

### 3. `GET /api/v1/shifts`

Token required. Query: optional `updatedSince` (the opaque `cursor` from the previous answer).

```json
{
  "full": false,
  "cursor": "<opaque>",
  "shifts": [ { "id": 41, "...": "the block's fields, see below" } ],
  "deleted": [ 38, 40 ]
}
```

- **No `updatedSince`, or a cursor older than 29 days or older than the account's `sync_reset_at`:** `full: true`,
  every block not in Recently deleted, and `deleted: []`. The phone replaces its whole copy.
- **Otherwise:** `full: false`, the blocks changed since the cursor that are not deleted in `shifts`, and the ids of
  blocks deleted since the cursor in `deleted` (still in Recently deleted, so the query includes deleted rows; the
  repository needs a native query because `Shift` hides them). A block deleted and then restored since the cursor
  appears in `shifts`, not `deleted`.
- **The cursor** is the latest change on the account: the greatest of its blocks' `sync_changed_at` (deleted rows included)
  and `sync_reset_at`, or a fixed starting value when there are none. Because it comes from the data and not the
  clock, an unchanged account gives the same answer. It is opaque to the app (for example base64url of a version and
  an instant). A cursor that can't be decoded answers 400 `invalid`. A cursor decoding to a time after the latest
  change is treated like any other cursor (the answer is empty); it never chooses an account or a record.
- **Late commits.** A save that commits after a read can carry a `sync_changed_at` a little before the cursor. Changed
  rows are selected from a fixed overlap before the cursor (5 minutes, as a named constant). The same block may come
  back twice; the app upserts by id, so that is harmless. Write the overlap in `docs/api-v1.md`.
- **`ETag` and `304`.** The response has a strong `ETag` computed from its body. A request whose `If-None-Match`
  matches answers `304` with no body. Responses are `Cache-Control: private, no-cache` (no shared caches, always
  revalidate).
- Order: by date, then start time, then id. No paging in this task; say so in the docs. The full list of a heavy driver
  is a few thousand small records.

**A block's fields** are the ones `ShiftResponse` has today, in the API's conventions: dates `2026-11-11`, local times
`18:30`, instants UTC with `Z`, money as strings with two decimals (`"72.00"`), status as lower-case codes (`scheduled`,
`completed`, `cancelled`, `forfeited`), documented in `docs/api-v1.md`. Map them in a new API record; don't change `ShiftResponse` or
the website's JSON. Nulls stay null.

### 4. `GET /api/v1/shifts/{id}`

Token required. 200 with one block in the same shape. 404 for an id that doesn't exist, belongs to another account or is
in Recently deleted. Same `ETag`/`304` behavior.

### 5. `GET /api/v1/home`

Token required. The figures the website's Home shows, computed on the server for the account's time zone, so the phone
needn't know the week rules:

```json
{
  "today": "2026-11-13",
  "week": {"from": "2026-11-09", "to": "2026-11-15", "...": "the statistics"},
  "lastSevenDays": {"from": "2026-11-07", "to": "2026-11-13", "...": "the statistics"},
  "goals": { "...": "goal progress" },
  "missingMiles": [ 37, 41 ]
}
```

- `today` comes from `UserTimeService` (the account's time zone and the server clock), never from the request.
- `week` is Monday to Sunday containing `today`, as `home.js` does. Both statistics objects come from
  `ShiftReportService.statistics` with the same filter the website sends, mapped with money as strings.
- `goals` is `ShiftReportService.goals`, mapped the same way. `missingMiles` lists the ids `ShiftService.missingMiles`
  returns for the website's default of 7 days.
- Scheduled blocks never count toward earnings, hours or net. That is already true in these services; a test proves it
  for this endpoint.
- `ETag`/`304` as above. No `updatedSince`: it is one small object.

### 6. Shared rules

- Everything is scoped to the token's account; no parameter can choose another account. The principal is the email the
  token filter sets, as in `GET /api/v1/account`.
- The endpoints exist only with `FLEXBUDDY_API_ENABLED=true`, in the API chain, like FB-005's. With it off they answer
  404 like every `/api/v1` path, and the new beans are absent.
- Controllers stay thin: queries and mapping live in services (for example an `ApiShiftService`), reusing
  `ShiftService` and `ShiftReportService`. No business rule is copied.
- `docs/api-v1.md`: a "Sync" section under Conventions (cursor, `full`, `deleted`, overlap, reset, the 29-day rule,
  `ETag`/`304`), and a section per endpoint in the page's shape with example JSON. Update the Status line.

## Acceptance criteria

- [ ] Every save, soft delete, delete all, restore and batch restore moves `sync_changed_at`; restored backup rows get
      the restore time. `updated_at` behaves exactly as before (a restored block doesn't show "last edited").
- [ ] `V30__sync.sql` adds and backfills `shift.sync_changed_at`, adds `app_users.sync_reset_at` and the
      `shift(owner_id, sync_changed_at)` index; the entity declares them; no committed migration changed.
- [ ] Permanent delete, empty trash, undoing a restore and a backup restore set `sync_reset_at` in the same transaction.
- [ ] `GET /api/v1/shifts` without a cursor returns every live block with `full: true`; with a cursor, only changed
      blocks and deleted ids; deleted-then-restored blocks come back as changed.
- [ ] A cursor older than 29 days or older than `sync_reset_at` gets `full: true`; an undecodable one gets 400 `invalid`.
- [ ] An unchanged account returns the same cursor and body; `If-None-Match` with its `ETag` returns `304` with no body.
- [ ] A save committed with a `sync_changed_at` inside the overlap before the cursor is still returned.
- [ ] `GET /api/v1/shifts/{id}` returns the block; another account's, a missing or a deleted id returns 404.
- [ ] `GET /api/v1/home` returns today, the Monday-to-Sunday week, the last seven days, goals and missing-miles ids in
      the account's time zone, matching the website's figures for the same account and dates.
- [ ] Scheduled blocks don't count toward any Home figure.
- [ ] Money is a two-decimal string everywhere in these responses; dates, times and instants follow the conventions.
- [ ] Missing or bad tokens get 401 `unauthorized`; browser sessions don't authenticate; with the API off every new
      path answers 404 and the beans are absent.
- [ ] The website's `/shifts` JSON and pages are unchanged (existing tests pass untouched).
- [ ] `docs/api-v1.md` documents the sync convention and the three endpoints.

## Security and regression risks

- **Per-user data:** every query joins on the token's account; tests use two accounts and try each other's ids.
- **Sync correctness:** a missed deletion leaves a ghost block, with its earnings, on the phone. The reset rule and the
  `sync_changed_at` set by the native queries exist for this; review every path that deletes or restores blocks.
- **Earnings:** figures come only from existing services; scheduled blocks are excluded; money is never a float.
- **Migration:** additive (two columns, a backfill and an index), safe to run on production's data; never edit V1 to
  V29. The backfill and index take a brief lock on `shift`, which is small. The migration test checks the backfill.
- **Backup/restore:** the backup format doesn't change; `sync_reset_at` is not backed up or restored.
- **Website:** `updated_at`, "last edited" and the `expectedUpdatedAt` conflict check must not change; tests that
  delete and restore a block prove it.
- **Disabled API:** production stays exactly as it is while `FLEXBUDDY_API_ENABLED` is unset.
- **Logging:** no tokens or `Authorization` headers in logs, as in FB-005.
- **Both catalogs:** no user-facing text is added (the API returns codes), so no catalog change is expected.
