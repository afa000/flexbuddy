# Task: FB-007 - Send a rejected "Keep me signed in" cookie to the sign-in page, not the error page

Status: Ready for implementation
Risk: high (sign-in)
Implementer: Claude Code (Sonnet)
Review: fresh Claude Code session (Opus), review-task skill

## Objective

When a driver's "Keep me signed in" cookie is out of date, FlexBuddy shows "Something went wrong" instead of the
sign-in page. It happened on October 26, 2026 at 01:20 UTC when the Play Store build (version 3) was opened on the
emulator. That was the only occurrence in Render's logs since October 12, but the second closed test starts now, and a
tester who sees it will report that the app broke. The driver should land on the sign-in page with the existing "Your
session expired. Sign in again." notice.

- `flexbuddy/src/main/java/com/angel/flexbuddy/config/SecurityConfig.java`: `rememberMeServices()` (lines 72-90) and

- `flexbuddy/src/test/java/com/angel/flexbuddy/config/RotationTolerantRememberMeServicesTest.java`: the unit tests,
  including `tokenReusedAfterGracePeriodIsStillTreatedAsTheft` and `tokenThatWasNeverIssuedIsTreatedAsTheft`.
- `flexbuddy/src/test/java/com/angel/flexbuddy/PersistentSignInIntegrationTest.java`: the integration tests for
  remember-me, including `concurrentRequestsWithTheSameRememberMeCookieKeepTheUserSignedIn`.
- `flexbuddy/src/main/resources/templates/login.html`: lines 59-61, the `param.expired` notice.
- Catalog keys (grep, don't open the files): `login.yourSessionExpiredSignIn` in `messages.properties` ("Your session

## Current behavior

Checked against `origin/main` at ca148da.

- When a remember-me cookie's series exists but its token doesn't match, and the token wasn't rotated in the last
  minute, Spring's `PersistentTokenBasedRememberMeServices.processAutoLoginCookie` deletes every remember-me token for
  the account (`removeUserTokens`) and throws `CookieTheftException`. `AbstractRememberMeServices.autoLogin` clears the
  cookie and throws it again. Nothing catches it, so the servlet fails with a 500 and the driver sees `error.html`
  ("Something went wrong"). An error alert email goes to the operator.
- The production log at 2026-10-26T01:20:05Z shows exactly this:
  `CookieTheftException: Invalid remember-me token (Series/token) mismatch`, thrown from
  `RotationTolerantRememberMeServices.processAutoLoginCookie` line 56.
- The remember-me filter runs on every request, public ones too (`/sw.js`, `/css/**`, `/login`). Any of them can be
  the one that gets the 500.
- `recentlyRotated` lives in memory, so a server restart (every deploy) forgets the last minute of rotations. That may
  be how a cookie went stale on October 26. Two deploys happened in the 15 minutes before it.

## Required behavior

1. **No error page.** A `CookieTheftException` from remember-me never becomes a 500 or the error page, on any request:
   pages, JSON requests, static files or the service worker.
2. **Keep the security response.** As today, every remember-me token for the account is deleted (the account is
   signed out on every device) and the cookie is cleared. Only what the driver sees changes.
3. **Page navigations go to sign-in.** A `GET` for a signed-in page (for example `/` or `/account`) made with the
   stale cookie redirects to `/login?expired`, which shows the existing "Your session expired. Sign in again." notice in
   the driver's language.
4. **Other requests carry on signed out.** A public page or static file (`/login`, `/privacy`, `/sw.js`, `/css/...`)
   is served normally, as for a visitor who isn't signed in. A JSON or fetch request to a protected endpoint gets
   exactly the answer it gets today with no session and no cookie. Check what that is before changing anything, and
   don't change it.
5. **A warning, not an alert.** Log one `WARN` line saying a reused remember-me cookie was rejected and the account's
   remember-me tokens were removed. Never put the email, series or token value in it. It must not trigger the error
   alert email.
6. **Nothing else changes.** The one-minute rotation grace, the 30-day lifetime, cookie attributes, sign-out, "Sign out
   everywhere" and two-step sign-in all behave as before.

A suggested shape: override `autoLogin` in `RotationTolerantRememberMeServices` to catch `CookieTheftException`, log
the warning and return `null`, so the request continues unauthenticated. Then, for the redirect, mark the request
(for example with a request attribute) so that the login entry point sends a page navigation to `/login?expired`
instead of `/login`. Any approach that meets the requirements and keeps the change small is fine.

## Out of scope

- Keeping the rotation grace across restarts (storing recently rotated tokens in the database). See the open
  questions.
- Changing what counts as theft, the grace period or the token lifetime.
- The `/api/v1` token sign-in in FB-005.
- Android, the catalogs, `error.html` and the error alert service.

## Design references

None. The page and notice already exist.

## Acceptance criteria

- [ ] A stale remember-me cookie on `GET /` redirects to `/login?expired`, clears the cookie, and removes the account's
      remember-me tokens.
- [ ] A stale cookie on `/login`, `/sw.js` or a CSS file gets a normal 200 response, not a 500.
- [ ] A stale cookie on a protected JSON endpoint gets the same response as a request with no session or cookie.
- [ ] One `WARN` log line with no email, series or token, and no error alert.
- [ ] The existing remember-me tests pass unchanged, including the grace-period and concurrent-request tests.
- [ ] The login page shows the notice in English and in Spanish.

## Validation

From the repository root: `.\scripts\verify.ps1 -TaskId FB-007`. No migration, so the PostgreSQL test has nothing new,
but CI runs it anyway.

New tests:

- **Unit** (`RotationTolerantRememberMeServicesTest`): `autoLogin` with a stale token returns `null` instead of
  throwing, clears the cookie, removes the user's tokens and logs the warning without the email or token values.
- **Integration** (`PersistentSignInIntegrationTest`): sign in with "Keep me signed in", use the cookie once so it
  rotates, move the injected clock past the one-minute grace, then send the old cookie to:
  - `GET /`: expect `302` to `/login?expired`;
  - `GET /sw.js` and `GET /login`: expect `200`;
  - a protected JSON endpoint: expect the same as with no cookie.

  In each case, check that the cookie is cleared and the account has no persistent tokens.
- **Rendering:** `/login?expired` shows the notice text from both catalogs.

**Local check** (`.\mvnw.cmd spring-boot:run`, local test account): sign in with "Keep me signed in". Copy the
`FLEXBUDDY_REMEMBER_ME` cookie, end the session, load a page so the cookie rotates, wait over a minute, then send the
old cookie (for example with `curl -b`). Expect the redirect to `/login?expired`, not the error page.

**After the deploy:** check Render's logs for the new warning and the absence of `CookieTheftException` stack traces.
Don't recreate the problem on the emulator: it is signed in to production as the Play Reviewer, and checks there are
read-only.

## Security and regression risks

- **Theft detection stays.** Spring's response (remove all tokens, clear the cookie) must still happen. The change
  only replaces the 500 with a sign-in redirect. A test must prove the tokens are removed.
- **No silent sign-in.** Returning `null` must leave the request unauthenticated. The old cookie must never sign
  anyone in.
- **Logs.** No email, series or token value in the warning.
- **The grace period** (`concurrentRequestsWithTheSameRememberMeCookieKeepTheUserSignedIn`) must still pass. Breaking
  it would sign drivers out on every app launch.
- **Per-user data, earnings, backups, migrations, catalogs and Android:** untouched.

## Open questions

1. **Keep the grace period across restarts?** Storing recently rotated tokens in the database would stop deploys from
   causing this, but it needs a migration and more sign-in code. With one occurrence in two weeks, wait and watch the
   new warning in the logs during the closed test. If it recurs after deploys, plan it as its own task.
2. **Sign out everywhere on theft?** Spring treats a stale token as theft and signs out every device. That's the safe
   default, and this task keeps it. If the warning shows it's mostly caused by restarts, revisit it together with
   question 1.
