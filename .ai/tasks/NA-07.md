# Task: NA-07 - Native API screenshot import (server half)

Status: Ready for implementation (owner's decisions of 2026-11-14 below; not yet committed)
Risk: high (screenshots carry a driver's pay; an import saves earned blocks; a retried or delayed save must never count
pay twice)
Implementer: Claude Code (Opus)
Review: fresh Claude Code (Opus), Codex (Sol) or Antigravity (Gemini 4 Argon) session, review-task skill

## Objective

Let the native app send a block screenshot and get back what the website's import reads from it (station, day, times,
base pay, tips, warnings, duplicate and scheduled-block matches), so the driver can review it and save it as a block
from the phone, including screenshots that waited on the phone while it was offline. Drivers must get exactly the
website's reading and rules, one save per screenshot however often the phone retries, and no copy of the screenshot or
its text kept anywhere on the server.

The app screens, the share intent and the phone's waiting-screenshot store are a separate task in `flexbuddy-android`
(next free id FB-037).

## Current behavior

- The website reads a screenshot with `POST /shifts/import-preview` (multipart field `screenshot`, session sign-in).
  `ShiftImportService.createPreview` checks the declared type (PNG or JPEG), decodes inside `ScreenshotReadGate` (one
  read at a time, 20 s wait, then 503 busy), refuses images over 12,000 px a side or 30 MP, subsamples above 5 MP,
  runs Tesseract, parses one block, applies `ImportWarningRules`, suggests `SCHEDULED` for a block that starts after
  "now" in the driver's zone, and asks `ScheduledShiftMatcher` for overlapping logged or scheduled blocks.
- The preview saves nothing and keeps nothing: the image lives only for the request. The answer carries the file name,
  size, the full OCR text and lines with boxes, per-field and overall confidence, and translated warning and duplicate
  sentences.
- The website's review does show read text and confidence to drivers (`templates/shifts.html` `#ocrDetails`, a
  collapsed "View extracted text" panel; `app.js` `renderRawText`, `highlightRawLine`, `renderReadQuality` and the
  per-field "N% read" / "Missing" badges in `setPreviewField`). What it uses for display: each line's `index` and
  `text` (one row per line; the line's own confidence and its box are not shown), `rawText` only when there are no
  lines, each field's `value`, `level`, `confidence` and `lineIndex` (focusing a field highlights its source line), and
  `meanConfidence` (the read-quality bar). It does not display `year`, line boxes, per-line confidence,
  `sourceLineRange`, the file name, type, size or `message`. The API returns exactly the displayed set (Decision 3).
- Saving is a separate, ordinary block write chosen by the driver: add the block (`POST /api/shifts`) or, for a
  `SCHEDULED_MATCH`, complete the scheduled block (`PATCH /api/shifts/{id}/status`), each with its own request id. The
  browser makes sure only one of the two goes out per screenshot. A batch (FB-021) is up to ten files read one at a
  time and saved one by one; duplicates inside a batch are found in the browser.
- Offline, the website can't read: the preview is network-only, and shared screenshots wait in the service worker's
  share inbox until the import screen reads them online.
- `/api/v1` has no import endpoint. NA-05 block writes (`POST /api/v1/shifts`, `PATCH /api/v1/shifts/{id}/status`)
  already require an `Idempotency-Key`, and keys are shared across every API write of the account, with the action
  and target in the receipt hash.

## Required behavior

Bearer-only, under `/api/v1`, registered only when `flexbuddy.api.enabled=true` (`@ConditionalOnProperty`, like
NA-05/NA-06). The website's import endpoint, services, pages, scripts and text catalogs do not change.

### Reading: `POST /api/v1/shifts/import-preview`

- `multipart/form-data` with one part `screenshot`. Same limits as the website, from the same properties and
  constants: PNG or JPEG only, at most 5 MB per file and 6 MB per request, 12,000 px a side, 30 MP; one read at a time
  through `ScreenshotReadGate`. No other parts; one screenshot per request (the phone sends a batch one at a time, as
  the website does).
- Calls `ShiftImportService.createPreview(email, screenshot)` with the token's account and maps its answer. No second
  parser, no copy of the import, warning, status-suggestion or duplicate rules in the API layer; if the mapping needs
  something the service doesn't expose, add it to the service so the website and API share it.
- Requires an `Idempotency-Key` (UUID, same parsing as NA-05). It is the screenshot's key: the phone creates one per
  screenshot when it is picked or shared and later saves that screenshot with the same key (see Saving). Before
  reading, the server looks up a receipt for that key on the account:
  - a receipt for a block write: `409 {"error":"already_saved","id":41}` without decoding or reading the image, so a
    waiting screenshot whose save landed (answer lost) is never offered again;
  - a receipt for an expense or payout write: `409 {"error":"idempotency_conflict"}`;
  - none: read as normal. The preview itself writes no receipt and consumes no key.
- **One preview in flight per account.** A small in-process per-account lock (for example a concurrent map of
  account id to a non-blocking lock; no new dependency) is taken before the receipt lookup and the read, and released
  in a `finally` on every path: success, `already_saved`, invalid upload, busy, read failure. A second preview from
  the same account while one is running is answered at once with `429 {"error":"busy_account"}` and a `Retry-After`
  header in seconds (for example the `ocr-wait` length), without touching the image or `ScreenshotReadGate`. Other
  accounts are not blocked by it (they still share the global one-at-a-time gate). The cap is per server instance; a
  second instance would allow one per account on each, which is acceptable while Render runs one. The lock map must not
  grow without bound (remove an account's entry when released, or equivalent). An oversize upload rejected before the
  controller never takes the lock.
- `200` JSON with `Cache-Control: no-store`, holding what the website's review shows drivers:

  ```json
  {
    "meanConfidence": 87,
    "lines": [{"index": 0, "text": "Amazon Flex"}, {"index": 3, "text": "DXX1"}],
    "rawText": null,
    "shifts": [{
      "station": {"value": "DXX1", "level": "high", "confidence": 91, "lineIndex": 3},
      "date": {"value": "2026-11-13", "level": "high", "confidence": 90, "lineIndex": 4},
      "startTime": {"value": "10:30", "level": "medium", "confidence": 72, "lineIndex": 5},
      "endTime": {"value": "13:30", "level": "medium", "confidence": 72, "lineIndex": 5},
      "basePay": {"value": "72.00", "level": "high", "confidence": 88, "lineIndex": 7},
      "tips": {"value": "18.50", "level": "high", "confidence": 88, "lineIndex": 8},
      "suggestedStatus": "completed",
      "warnings": [{"code": "medium_confidence", "severity": "info", "field": "startTime"}],
      "duplicates": [{"shiftId": 41, "kind": "scheduled_match"}]
    }]
  }
  ```

  Every value is copied from the `ShiftImportPreviewResponse` that `createPreview` returns; the API layer only renames
  enums to lower case and formats dates, times and money. It doesn't recompute levels, confidences, line indexes or
  warnings. `meanConfidence` and each field's `confidence` are integers 0-100 (`confidence` is null when the field
  wasn't read or was defaulted without a line); `level` is `high`, `medium`, `low` or `missing`, so the phone can draw
  the website's "N% read" and "Missing" badges and read-quality bar with the website's thresholds. `lines` are the OCR
  lines in order with `index` and `text`; a field's `lineIndex` points at one of them, so the phone can highlight the
  source line. `rawText` is the website's fallback, sent only when `lines` is empty (otherwise null). A missing field is
  `{"value": null, "level": "missing", "confidence": null, "lineIndex": null}`. API conventions apply: lower-case codes,
  ISO dates, local times without seconds, money as strings. Warnings and duplicates carry codes only, never the
  website's translated sentences (the app has its own text). The phone looks the matched block up in its synced cache
  (or `GET /api/v1/shifts/{id}`) for its station, day and `updatedAt`. `shifts` is an array to match the website,
  always one entry today. Not returned, because the website review doesn't show them: line boxes, per-line confidence,
  `sourceLineRange`, `year`, file name, content type, size and the website's `message`.
- Errors, never echoing the image, its text or the file name:
  - `400 {"error":"invalid","reason":"error.import.<key>"}` for the service's `InvalidScreenshotException` keys
    (`noScreenshot`, `unsupportedType`, `notReadableImage`, `couldNotRead`, `tooLargeSides`, `tooLargeMegapixels`).
    A missing or malformed key is `400 {"error":"invalid","fields":{"Idempotency-Key":"invalid"}}`; a request that
    isn't multipart is `400 {"error":"invalid"}`.
  - `413 {"error":"too_large"}` when the multipart limits are exceeded, as JSON from the API, not the website's error
    page. This exception is raised before the controller, so a controller-local handler won't see it; test it.
  - `429 {"error":"busy_account"}` with `Retry-After` when this account already has a preview in flight.
  - `503 {"error":"busy"}` when the reader stays busy past the wait, not logged as an error (as the website).
  - `500 {"error":"read_failed"}` when Tesseract fails, logged once with the exception class only, as the website.
  - `401`, and `404` with the API off, as every API path. Authentication is checked before the upload is read.

### Saving: existing NA-05 writes, no new write endpoint

- The driver's review ends in one of the NA-05 writes the website's import also ends in: `POST /api/v1/shifts` (add,
  as reviewed, `completed` or `scheduled` by the driver's explicit choice, FB-011) or
  `PATCH /api/v1/shifts/{id}/status` to `completed` for a `scheduled_match`, with that block's `expectedUpdatedAt`.
  Both go through `ShiftService` as today; earnings rules and validation are unchanged, scheduled blocks never count.
- The phone sends either one with the screenshot's key. Because NA-05 receipts hash the action and target, the second
  of "add" and "complete" for the same screenshot is refused with `409 idempotency_conflict` once the first has landed,
  so a screenshot's pay can never be counted twice, even when an outbox retries or the driver changes the choice after
  an unanswered save. A changed value after a landed save is the same `409`. Add a test that proves this across the two
  endpoints; change NA-05 code only if the test shows it doesn't hold.
- A stale scheduled block (edited, completed or deleted on the website since the preview) answers the normal NA-05
  `409 conflict` or `404`; the phone re-reviews. No server-side duplicate blocking on add: as on the website and in
  NA-05, the duplicate list is a warning the driver answers, and duplicates inside one batch are the phone's to find
  from its own saves, like `import-queue.js savedMatch`.
- No batch endpoint (FB-021 saves one by one), no migration, no new table and no new receipt kind. The next free
  migration number is V33; this task doesn't use it.

### Privacy and logs

- Nothing about a screenshot is kept after the request: no file, database row, cache entry, receipt field or log line
  holding the image, its read text (`lines`, `rawText`), the confidence values, the parsed values or the file name.
  The answer must carry `Cache-Control: no-store`. Spring Security's default headers may already add it; set it
  explicitly on this endpoint anyway (API reads set `private, no-cache` for ETags, which must not leak onto it) and
  test the header. Don't change the website. The multipart part is the container's
  temporary part, deleted at the end of the request as the website's is. Nothing new is added to backups.
- The API's error handlers and any new log or alert line carry codes and exception classes only. A test captures the
  log output of a preview and of each failure path and asserts that none of the made-up OCR line texts, the raw
  text, the parsed values or the file name appear.
- Never log the token, `Authorization` or `Idempotency-Key` with the screenshot.
- **For the Android half (FB-037), to carry into its spec:** the read text is screenshot content. The phone holds the
  preview answer (lines, raw text, confidences) in memory only for the review screen; it is never written to Room, the
  outbox, DataStore, files or logs (including crash reports), and is cleared when the review closes and at sign-out.
  Only the saved block's reviewed values go into the outbox.

## Acceptance criteria

- [ ] `POST /api/v1/shifts/import-preview` returns the same station, day, times, pay, tips, suggested status, warning
      codes and duplicate matches as `POST /shifts/import-preview` for the same screenshot, account and clock, through
      `ShiftImportService` (no duplicated rules); with the API off it is 404 and no new bean is registered.
- [ ] The answer carries the website review's read lines (`index`, `text`), raw-text fallback, `meanConfidence` and
      each field's `value`, `level`, `confidence` and `lineIndex`, equal to `createPreview`'s values; it carries no
      line boxes, per-line confidence, `sourceLineRange`, `year`, file details or translated sentences, and is sent
      with `Cache-Control: no-store`.
- [ ] A second concurrent preview from the same account answers `429 busy_account` with `Retry-After` without reading;
      the lock is released after success, `already_saved`, invalid and failed reads, and an oversize upload never
      holds it; a preview from another account at the same time is not refused with `429`.
- [ ] Type, size, side and megapixel limits, busy, read failure, missing screenshot, non-multipart and missing key
      answer the documented codes as JSON; an over-limit upload is `413` JSON, not HTML.
- [ ] A key that already saved a block answers `409 already_saved` with its id and never runs OCR; a key used for an
      expense or payout answers `idempotency_conflict`; a preview consumes no key.
- [ ] With one key, add then complete (and complete then add) for the same screenshot apply once and answer
      `idempotency_conflict` the second time; delayed retries are acknowledged; NA-05 and NA-06 tests pass unchanged.
- [ ] Duplicates match only the token's own blocks; another account's blocks never appear.
- [ ] No image, read text, confidence, parsed value or file name is stored, cached (`no-store`) or logged on any path.
- [ ] `docs/api-v1.md` updated; checks run and not run reported in `.ai/implementations/NA-07.md`.

## Security and regression risks

Per-account scoping of the duplicate matcher, receipt lookup and preview lock (a lock that leaks on an error path
would lock an account out of imports until restart); double-counted pay if add and complete could both land
for one screenshot; earnings rules for scheduled blocks; memory on Render's small instance (the gate and decode limits
must cover the API path too, and nothing may read the whole part into a byte array outside the gate); upload size
limits answering before any image work; screenshots, OCR text and file names staying out of storage, logs, alerts and
error bodies; website import behavior and its Spanish and English text unchanged; NA-05/NA-06 behavior unchanged; API
still off by default.

## Decisions (owner, 2026-11-14)

1. **Saving** goes through the existing NA-05 block writes with the screenshot's key. No dedicated import-save
   endpoint.
2. **The preview requires the screenshot's `Idempotency-Key`**, and a key that already saved a block answers
   `409 already_saved` with the block id, without OCR.
3. **The answer matches the website's review** (revised the same day): the read text as the website shows it (lines
   with index and text, raw-text fallback) and the confidence values (per field and overall, as numbers), plus the
   warning codes, all taken straight from `ShiftImportService`'s preview with no recomputation. Reasons: drivers get
   the same review on the phone as on the website, and one source of values keeps the two from drifting. Anything the
   website review doesn't show stays out. Because the read text is screenshot content, the nothing-stored,
   nothing-cached, nothing-logged rule covers it explicitly on the server, and FB-037 keeps it in memory only.
4. **Pacing**: at most one preview in flight per account, through an in-process per-account lock (no new dependency,
   per server instance). A concurrent second preview gets `429` with `Retry-After`; the phone sends previews one at a
   time and backs off on `429`. No per-minute rate.
