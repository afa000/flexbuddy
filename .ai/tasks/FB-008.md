# Task: FB-008 - Warn before importing a block that is already logged

Status: Ready for implementation
Risk: medium (import UI and one service; no change to how earnings are calculated)
Implementer: Antigravity
Review: fresh Claude Code session (Opus), review-task skill

## Objective

Drivers screenshot the same block more than once: when they accept it, when they check it the day before, and after
they finish it. The owner's own sample set has one block screenshotted three times. Today FlexBuddy saves every import,
so the same block is counted two or three times in hours, earnings, payouts, goals, the tax estimate and the block
evaluator's "you usually net" figure. Before saving an imported block, FlexBuddy should say when that block is already
logged and make adding it again a deliberate choice.

## Current behavior

Checked against `main` at 5b45efe, and reproduced on `localhost` on October 30, 2026 with a new test account.

1. Importing a "Schedule details" screenshot of a past block (VEA7, Oct 19, 4:45-9:15 PM, $119.50) and tapping
   **Add shift** saves a completed block.
2. Importing the same screenshot again shows the review form with no notice, and **Add shift** saves a second, identical
   block. Home then lists both, and Reports, the payout for that week and the evaluator's VEA7 average all count it
   twice.
3. A completed import is matched only against **scheduled** blocks (`SCHEDULED_MATCH`, "This looks like your scheduled
   VEA7 block on ... Complete it?"). An already **completed** block is never matched.
4. A future-dated import (suggested status `SCHEDULED`) is never matched against anything, so screenshotting an accepted
   block twice gives two scheduled blocks. Both show on Schedule, and both count toward "expected pay".

## Required behavior

1. **Find completed and scheduled blocks.** For an imported block with a date and both times, look for the caller's
   blocks with status `COMPLETED` or `SCHEDULED` that overlap it by at least 30 minutes, using the existing overlap
   and station rules. That includes blocks that run past midnight, as `comparesBlocksThatRunPastMidnight` does today.
   Also look at the day before, so a block that started late the previous evening is found. Cancelled, forfeited and
   deleted blocks are never matches.
2. **Kinds.**
   - An existing **scheduled** block, when the import is suggested as `COMPLETED`, stays `SCHEDULED_MATCH`, with the
     same message and behavior as today.
   - Every other match is `EXACT` when the date, start time and end time are all equal, and `LIKELY` otherwise. That
     covers a completed block for either kind of import, and a scheduled block for a scheduled import.
   - Each match is returned once, with the existing block's id.
3. **Message.** `EXACT` and `LIKELY` use a new key `import.alreadyLogged`:
   - English: `You already have a {0} block on {1} at {2}.`
   - Spanish: `Ya tiene un bloque de {0} el {1} a las {2}.`

   The arguments are the existing block's station, its day in `Messages.dayFormat`, and its start time in
   `Messages.timeFormat`, in the driver's language.
4. **Review form.** When the preview has an `EXACT` or `LIKELY` match:
   - Show a notice in the review form, above Status. Use the same style as `#scheduleMatchNotice`, with
     `role="status"`. It shows the message and an **Open it** button (new key `import.openIt`, "Open it" / "Abrirlo").
     The button fetches `GET /shifts/{id}` and opens that block in the existing edit dialog (`openEditModal`).
   - The save button reads **Add anyway** (new key `js.app.addAnyway`, "Add anyway" / "Agregar de todos modos"),
     whatever the status. Saving still works: OCR can misread a time, and a driver may really have two blocks that
     overlap. The button gets its normal label back when the notice goes away.
   - When this notice shows, the "Complete this scheduled shift" notice does not.
5. **Edits.** If the driver changes the date, start time, end time or station in the review form, hide the duplicate
   notice and restore the normal button label. The match was for the values that were read, not the edited ones.
   **Start over** and choosing a different screenshot clear it as well.
6. **Shared screenshots.** A screenshot shared from the phone's share sheet goes through the same preview, so it gets
   the same notice. Check this; no separate change is expected.
7. **Offline.** The import preview already needs a connection. Nothing about the outbox changes.

## Out of scope

- Adding a block by hand, duplicating a block, and restoring a backup. Restore already skips rows it has, by date,
  start and station.
- Merging or deleting duplicates already saved. A driver can delete them; Recently deleted keeps them for 30 days.
- Any change to OCR, the parser, the warnings in `ImportWarningRules`, or the 30-minute threshold.
- Earnings, net and tax calculations. They change only because fewer duplicates get saved.

## Design references

None. Reuse the schedule-match notice's look.

## Acceptance criteria

- [ ] Importing a screenshot of a block that is already **completed** shows the notice and an **Add anyway** button.
      Tapping it saves the block. **Open it** opens the existing block in the edit dialog.
- [ ] Importing a screenshot of a block that is already **scheduled**, with a future date, shows the same notice.
- [ ] A past block that has a matching **scheduled** block, and no completed one, still shows "Complete this
      scheduled shift" exactly as today.
- [ ] A cancelled, forfeited or deleted block is never reported as a match.
- [ ] A different station, or an overlap under 30 minutes, gives no notice.
- [ ] Editing the date, times or station in the review form hides the notice and restores **Add shift**.
- [ ] Messages and button labels appear in English and Spanish, and `SpanishMessagesTest` passes.
- [ ] Matching only ever reads the signed-in driver's blocks.

## Security and regression risks

- **Per-user data:** matching reads only the signed-in account's blocks. The `Open it` fetch uses the existing
  owner-scoped `GET /shifts/{id}`.
- **Earnings:** no calculation changes. The existing "Complete this scheduled shift" flow, which turns a scheduled block
  into a completed one, must keep working, because it is how scheduled blocks get counted.
- **Catalogs:** three new keys, in the same comment group in both files. Spanish keeps `{0}`, `{1}` and `{2}`.
- **Backups, migrations and Android:** untouched.
