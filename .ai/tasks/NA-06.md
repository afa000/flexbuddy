## Objective

Let the native app list, add, edit, delete and restore expenses, and see and record payouts, including from its
offline outbox, with the same rules as the website. Drivers must get the same net and tax figures on the phone as on
the website, and a retried or delayed write must never add an expense twice or overwrite a later change.

The app screens (including the FB-014 effect-on-net message) are a separate task in `flexbuddy-android`.

## Current behavior

- `/api/v1` has blocks only (read, sync, writes). Expenses and payouts exist only on the website
  (`/api/expenses`, `/api/payouts/{payoutDate}`, `/api/shifts/pay-periods`).
- `expense` has `updated_at` and `deleted_at` but no sync column; soft delete and restore are bulk updates that may not
  move `updated_at`. Permanent delete, emptying Recently deleted and the 30-day purge leave no trace.
- Website expense creates are idempotent through `create_request_id`; edits, delete and restore have no keys.
- Payouts are one row per payout date, replaced on re-record and hard-deleted on remove. Pay-period figures are
  computed from blocks and settings when shown.
- `api_write_receipt.shift_id` is `not null`, so receipts can only point at blocks.

## Required behavior

All endpoints under `/api/v1`, bearer-only, registered only when `flexbuddy.api.enabled=true`
(`@ConditionalOnProperty`, like NA-05). Existing website endpoints, services' behavior and pages do not change.

### Expenses

- `GET /api/v1/expenses` with change-only sync exactly as `GET /api/v1/shifts`: no `updatedSince` gives
  `full: true` and every live expense; a cursor gives changed live expenses plus `deleted` ids; same overlap, 29-day
  limit, opaque cursor, strong `ETag`/`304`, `Cache-Control: private, no-cache`. Its own cursor (expense changes);
  the account's `sync_reset_at` also makes it full.
- `GET /api/v1/expenses/{id}`: one live expense; another account's or a deleted one is 404.
- An API expense carries: `id`, `date`, `category` (lower case), `amount` (money string), `note`, `shiftId`,
  `createdAt`, `updatedAt`. It does not carry `counts`, the station or "block deleted": those depend on the block,
  which doesn't change the expense row, so sync would not refresh them. `docs/api-v1.md` states the rule the phone
  applies from its block cache, matching `ExpenseService.countable`/`countedStation`: an expense linked to a block that
  is still scheduled does not count yet; one linked to a deleted or unknown block counts by its own date, unlinked.
- Writes, each through `ExpenseService` with `ExpenseRequest` validation:
  - `POST /api/v1/expenses` (201 + `Location`, `{"id":n}`)
  - `PUT /api/v1/expenses/{id}` (200, `{"id":n}`)
  - `DELETE /api/v1/expenses/{id}?expectedUpdatedAt=` (204)
  - `POST /api/v1/expenses/{id}/restore` (200, `{"id":n}`), only within 30 days of deletion, refused at exactly 30
    days even if the purge has not run.
  No batch restore, permanent delete or empty-trash endpoints.
- Linking: `shiftId` must be the account's own live block (another account's id is 404, as the website), and an
  unchanged link to a block now in Recently deleted is kept, as `ExpenseService.apply` does today.
- `sync_changed_at` on `expense` moves on create, edit, soft delete (single and the block-delete batch path, if any)
  and restore (single and batch). Permanent delete, emptying Recently deleted and the 30-day purge call
  `markSyncReset` so phones reload, the same way blocks do. Backup restore already marks the reset; check expenses
  restored from a backup get a `sync_changed_at`.

### Payouts

- `GET /api/v1/payouts?count=n` returns the pay periods from `ShiftReportService.payPeriods` (same default and limits
  as the website) mapped to API shapes: dates as ISO dates, money strings, status lower case, plus each recorded
  deposit's `updatedAt` (null when nothing is recorded) for use as the write version. These figures depend on blocks
  and settings, so this endpoint is not change-only: every answer is full, with a strong `ETag`/`304`. Document this
  exception under Sync.
- `PUT /api/v1/payouts/{payoutDate}` with `{amount, note, expectedUpdatedAt}` through `PayoutService.record` and its
  rules (not in the future, must be a payout day; their message keys become `reason` codes in a 400).
  `expectedUpdatedAt` is the deposit's `updatedAt` the phone saw, or null to mean "nothing recorded"; a mismatch is
  409 `conflict` with the current deposit (or null).
- `DELETE /api/v1/payouts/{payoutDate}?expectedUpdatedAt=` through `PayoutService.remove`; 204. Same version rule.

### Retries and receipts

- Every write requires a UUID `Idempotency-Key`. Reuse the NA-05 receipt mechanism: account lock first, receipt lookup
  before the version check, hash of action + target + bound body + expected version, receipt saved in the same
  transaction, key reuse with a different request is 409 `idempotency_conflict`, failures don't consume a key, receipts
  last until account deletion. Keys are shared across all API write endpoints of the account, so a block key can't be
  replayed as an expense write.
- Existing-record writes require `expectedUpdatedAt` (microsecond comparison, after locking the owned row) and answer
  409 `conflict` with the current record when stale, so a delayed outbox write never overwrites a website change.
- Expense create also passes the key to `ExpenseService.create(..., requestId)` so a website create and an API create
  with the same key can't both add a row.
- New migration `V32__...sql` (next free number; never edit V31) that lets a receipt point at a block, an expense or a
  payout date: for example drop `not null` on `shift_id`, add nullable `expense_id bigint` and `payout_date date`, and
  a check that exactly one is set. No foreign keys to the targets (a retry after permanent deletion must not recreate
  data), no payload stored. Also adds `expense.sync_changed_at` (backfilled from `updated_at`/`deleted_at`, then
  `not null`) and an `(owner_id, sync_changed_at)` index. Hibernate mapping and `PostgresMigrationTest` assertions to
  match.
- Prefer extracting the shared key/lock/receipt/hash code from `ApiShiftWriteService` into one helper over copying it;
  block behavior and its tests must stay unchanged.

## Security and regression risks

Per-account scoping on every query and link (an expense can't be linked to another account's block); net and tax
figures (scheduled-block expenses, deleted-block expenses); the receipt migration and its transaction; sync
correctness after bulk updates and purges; Recently deleted 30-day window; backup/restore compatibility (receipts and
the new column stay out of the backup format); NA-05 block behavior unchanged; API still off by default.
