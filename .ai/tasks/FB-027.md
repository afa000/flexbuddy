## Objective

Drivers are protected by two rules that today depend on an agent remembering them: pushing to `main` is a release, and
a migration that has run in production must never change. This task makes Claude Code refuse both mechanically. It
also brings the workflow docs in line with how the owner actually works (since FB-011 every task has been handed to
Claude Code with Opus), and prepares this repository for the native app plan (`docs/native-app-plan.md`, NA-01 "In
this repository"): the `/api/v1` rule, the API contract file, and the free local test tools.

## Current behavior

- There is no `.claude/settings.json` and no hook. Nothing stops an agent from running `git push origin main`,
  `git push` while on `main`, or `gh pr merge`, all of which deploy production through Render.
- Nothing stops an edit to an existing `flexbuddy/src/main/resources/db/migration/V<n>__*.sql`.
- Claude Code doesn't load `.agents/skills/`; the docs tell the owner to type "Follow .agents/skills/<name>/SKILL.md".

- No rule covers `/api/v1`, no API contract file exists, and the setup guide doesn't cover running the PostgreSQL
  migration test locally or catching mail.

## Required behavior

### 1. Claude Code hooks (`.claude/settings.json`, committed)

Two `PreToolUse` hooks, written as Node scripts in `.claude/hooks/` (Node 22+ is already required; `jq` is not
installed). Each refusal exits with code 2 and a one-line reason on stderr that tells the agent the owner does this
step themselves.

- **Release guard** on `Bash|PowerShell`. Refuse, in any part of a chained command (`&&`, `||`, `;`, `|`, newline):
  - `git push` whose refspec targets `main` (`main`, `HEAD:main`, `x:main`, `+main`, `refs/heads/main`, `:main`);
  - `git push --all` or `--mirror`;
  - `git push` with no refspec while the current branch is `main`;
  - `gh pr merge` (merging is the owner's step; it deploys).
  Pushing a feature or `ai/` branch, `git push -u origin ai/FB-027`, `git status`, and commands that only mention
  "push" or "main" in text are allowed.
- **Migration guard** on `Edit|Write|MultiEdit|NotebookEdit`. Refuse when the target path is a
  `db/migration/V<n>__*.sql` file that git already tracks. Creating a new, untracked migration is allowed.
- Both scripts keep their logic in exported functions, with Node tests in `scripts/hooks/guards.test.mjs` (moved there by section 7)
  (`node --test ".claude/hooks/*.test.mjs"`). They fail open on unreadable input (exit 0), so a broken hook never blocks ordinary
  work, and they never print the command or file contents beyond the refused part.

### 2. Skill shortcuts for Claude Code

`.claude/skills/implement-task/SKILL.md`, `prepare-review/SKILL.md` and `review-task/SKILL.md`: short wrappers with the
same name and description that tell Claude Code to follow the matching `.agents/skills/<name>/SKILL.md`. The
`.agents/skills/` files stay the single source for the steps, so Antigravity and OpenCode are unaffected.

  change, and every API change updates `docs/api-v1.md`;
- Claude Code's hooks refuse pushes to `main`, `gh pr merge` and edits to existing migrations; don't work around them.

## Added scope (owner, November 11, 2026, before the first push)

The owner asked for four more things in the same task: the workflow must start in Codex with Sol and Terra in place
of Opus and Sonnet, Antigravity must work reliably, OpenCode should get its useful upgrades, and the workflow should
be more thorough while spending fewer tokens. Facts found while checking:

- Codex (desktop app; the CLI isn't on PATH) reads `AGENTS.md` and `.agents/skills/*/SKILL.md` itself, invoked as
  `$implement-task`. `~/.codex/config.toml` already sets `model = "gpt-6.1-sol"`, `model_reasoning_effort = "high"`
  and trusts this folder, so project `.codex/` hooks and rules load. Terra is `gpt-6.1-terra` (CLI 0.159.0+). Codex
  hooks use the same `PreToolUse` shape as Claude Code (`tool_input.command`; exit 2 blocks) and must be approved once
  in `/hooks`. Codex edits files with `apply_patch`, whose patch text names each file (`*** Update File: <path>`).
- All four Antigravity runs (FB-008, FB-009, October 30) ended with "a tool required the command permission that
  headless mode cannot prompt for" after about 40 `git grep` calls and up to 430 s. Antigravity 1.4.12's docs now say
  a denied tool is soft-denied and the run continues. Whether the sandbox can write this OneDrive folder is not
  documented.
- OpenCode is 2.1.2. It translates the version 1 `opencode.json` (checked with `opencode debug config`), so the rules
  still apply, but the file should be in the version 2 format. Version 2 reads `.agents/skills`, has `instructions`,
  `compaction` and `watcher.ignore`, and permission rules where the last match wins.

- Pipe-test each hook script with a sample `PreToolUse` payload, then trigger each live: a harmless refused command

- No browser, emulator or production check: nothing a driver sees changes.

## Security and regression risks

- A guard that is too broad blocks ordinary work (feature-branch pushes, `git status`); the tests cover the allowed
  cases. A guard that is too narrow gives false confidence; the docs say the hooks back up the rules, they don't
  replace them, and that a shell command could still edit a file the Edit guard doesn't see.
- Hooks run on the owner's machine for every tool call: keep them fast and dependency-free, fail open on bad input,
  and never log commands or file contents.
- No secrets in the Docker and Mailpit instructions; the container defaults are local throwaways.
- Sign-in, per-user data, earnings, migrations, backup/restore, catalogs and Android: untouched.
