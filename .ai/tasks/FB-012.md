# Task: FB-012 - Move a block wrongly marked Completed back to Scheduled

Status: Ready for implementation
Risk: high (status decides earnings, hours and net; the correction clears saved details)
Implementer: Claude Code (Opus). The owner handed this task to this session on November 5, 2026.
Review: fresh Claude Code session (Opus), review-task skill

Source: DX-02 in `docs/driver-experience-plan.md`. Builds on FB-011 (DX-01).

## Objective

Before FB-011, the import review preselected Completed, so some drivers have upcoming blocks saved as Completed. Their
pay already counts toward earnings, hours and net. Today the only fix is to delete the block and add it again:
Scheduled is disabled in the edit dialog for a completed block, and `ShiftService.applyRequest` refuses the change
(`error.shift.completedCannotReschedule`).

A driver should be able to say "I haven't worked this yet" and move the block back to Scheduled on purpose, seeing
exactly what that clears, with a short Undo.

## Current behavior

- The edit dialog disables the Scheduled option for any saved block that isn't Scheduled.
- `PUT /shifts/{id}` and `PATCH /shifts/{id}/status` refuse Completed, Cancelled or Forfeited to Scheduled.
- Linked expenses count by their own date in net figures, whatever the linked block's status.
- Payout reconciliation computes expected pay from completed blocks; recorded deposits are separate rows.

## Required behavior

### Server

1. New endpoint `POST /shifts/{id}/not-worked`, body `{"expectedUpdatedAt": "<the shift's updatedAt>"}` (required),
   optional `Idempotency-Key` header. It calls a new `ShiftService.markNotWorked(email, id, expectedUpdatedAt,
   requestId)`, `@Transactional`.
2. `markNotWorked`, in this order:
   - looks the block up by id **and owner** (404 `ShiftNotFoundException` otherwise);
   - a repeat under the block's `lastRequestId` returns the block as it is;
   - when `expectedUpdatedAt` differs from the block's `updatedAt` (microsecond precision, as in `changeStatus`),
     nothing is written and 409 `ShiftConflictException` returns the current block;
   - only a **Completed** block can be corrected; any other status is refused with 400
     `error.shift.onlyCompletedNotWorked`;
   - sets status Scheduled and `statusChangedAt`; keeps station, date, times and base pay (now the offered pay);
     sets tips to 0 and clears miles, odometer readings, actual start/finish, stops, packages and returns;
     `lateForfeit` false; stores the request id as `lastRequestId`.
   - Linked expenses stay linked and unchanged.
3. The guard in `applyRequest` stays: `PUT` and `PATCH .../status` still refuse Completed/Cancelled/Forfeited to
   Scheduled. Cancelled and forfeited blocks get no correction path.
4. No schema change and no migration. Backups need no change: a corrected block is an ordinary scheduled block.

### Edit dialog

5. For a saved Completed block, the dialog shows a "Not worked yet?" text button next to Duplicate. It's hidden for
   new blocks and other statuses, and disabled offline like Delete and Duplicate (`applyOfflineEditState`).
6. The button opens a confirmation panel in place of the form actions, like Delete:
   - title: move this block back to Scheduled?
   - it stops counting toward earnings, hours and net;
   - "This clears:" followed by the saved values that will be cleared, only the ones present: tips (amount), miles,
     odometer readings, actual times, stops/packages/returns; or "Nothing else changes." when none are present;
   - linked expenses stay as they are;
   - unsaved edits in the dialog are not saved;
   - Cancel (back to the form, nothing sent) and "Move to Scheduled".
   The list is built by an exported function in a new script (`static/js/not-worked.js`) from the saved block, so it
   can be tested in Node.
7. Confirming sends the request with the block's saved `updatedAt` and a new request id. On success the dialog closes,
   Home/Schedule reload, and a toast says the block is back in Scheduled with **Undo** (8 seconds, like other undos).
   On 409 the panel closes and the dialog shows that the block changed elsewhere and to reopen it. Other errors show
   the server's message. The button can't be pressed twice while the request runs.
8. Undo puts the block back exactly as it was saved: status Completed, tips, miles and every detail, through the
   existing `PUT /shifts/{id}` (Scheduled to Completed is already allowed). `undoEdit` sends the previous status.

## Out of scope

- Any change to how earnings, hours, miles, net, reports or payouts are calculated. They already leave out scheduled
  blocks.
- Cancelled or forfeited to Scheduled; the import flow (FB-011); multi-file import; per-block paid tracking (DX-12).
- Keeping cleared values after the Undo toast closes (owner chose clear-with-Undo on November 5, 2026).
- Offline queueing of the correction.

## Acceptance criteria

- [ ] A Completed block can be moved to Scheduled from the edit dialog without deleting and re-adding it.
- [ ] After the correction the block has no earned pay, net or counted miles, and drops out of earnings, hours,
      reports and expected payouts like any scheduled block; base pay is kept as the offered pay.
- [ ] The confirmation lists exactly the values that will be cleared; Cancel sends nothing and changes nothing.
- [ ] Tips, miles, odometer, actual times and route are cleared; linked expenses keep their link and amounts.
- [ ] Undo restores status and every cleared value.
- [ ] Another account's block gives 404; a stale `expectedUpdatedAt` gives 409 and writes nothing; a repeat with the
      same request id returns the block without applying anything twice; a non-Completed block gives 400.
- [ ] `PUT` and `PATCH .../status` still refuse moving a block that happened back to Scheduled.
- [ ] English and Spanish catalogs carry every new key in matching groups.

## Security and regression risks

- Ownership: the lookup must be scoped to the signed-in user.
- Data loss: values are cleared; the confirmation lists them and Undo restores them for 8 seconds only.
- Stale or repeated requests: `expectedUpdatedAt` plus the request id.
- Earnings: no calculation changes; scheduled exclusion is relied on, not reimplemented.
- Backup/restore and the 30-day Recently deleted window are untouched.
