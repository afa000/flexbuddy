# Plan: confirm the email address with a 6-digit code at sign-up

Planned against `origin/main` at 5de206b. Decided: the code is
**required before first use**, and existing accounts count as verified.

## Where things stand

- **Sign-up:** `POST /register` (`AccountController` line 93) validates,
  calls `AccountService.register` and redirects to `/login?registered`.
  Anyone can create an account with any address, including someone
  else's. Password-reset emails for that account then go to the real
  owner of the address.
- **Mail:** works through `MailConfig`. It uses `SmtpPasswordResetMailer`
  (async on `mailExecutor`) when `spring.mail.host` is set, and otherwise
  `LoggingPasswordResetMailer`.
- **Reset tokens:** `PasswordResetService` stores SHA-256 hashes of
  tokens, with expiry and single use, in `password_reset_token` (V21,
  `@OnDelete(CASCADE)`).
- **`AttemptLimiter`:** has buckets for sign-in, sign-up and reset.
- **`userDetailsService`** (`SecurityConfig` line 45) builds plain
  enabled users.

  **Note:** Spring checks "disabled" *before* it checks the password. A
  disabled flag would therefore tell anyone who types an email that the
  account is unverified, and could be used to trigger emails. This plan
  checks verification only **after** a correct password.
- **Test fixtures:** 28 test files build `new AppUser(...)` directly and
  then sign in. Whatever the new flag defaults to in the entity must
  keep those users verified.

## 1. Goal and out-of-scope

**Goal:**
- **Sign-up:** after Create account, the driver lands on a **Check your
  email** page. A 6-digit code arrives by email and lasts 15 minutes.
  Entering it verifies the account and signs the driver in, honouring
  "Keep me signed in" in the Play app the same way the sign-in page does.
- **Unverified sign-in:** an unverified account that signs in with the
  right password goes to the same page, with a fresh code. It's never
  signed in until verified.
- **Abandoned sign-ups:**
  - Unverified accounts are deleted after 24 hours.
  - Signing up again with an address that only has an *unverified*
    account replaces it, so nobody can block someone else's address by
    registering it first.
- **Existing accounts** are verified by the migration and never see the
  page.
- **Password reset** also verifies an account, because the reset link
  proves the driver owns the address.
- **Code storage** is reusable by the two-factor plan (`purpose`
  column).

**Out of scope:**
- Two-factor sign-in, which reuses this storage in `plan/two-factor`.
- Google sign-in.
- Changing the email on an existing account.
- SMS.
- Magic-link sign-in.

## 2. Data model and migration

New `src/main/resources/db/migration/V24__email_verification.sql`:

```sql
-- Existing accounts count as verified; only new sign-ups start unverified.
alter table app_users add column email_verified boolean not null default true;

-- Short numeric codes sent by email. Only a keyed hash is stored; each code works once, expires, and allows a few
-- wrong tries. The purpose column lets two-factor sign-in reuse the table.
create table email_code (
    id bigint generated by default as identity primary key,
    owner_id bigint not null references app_users(id) on delete cascade,
    purpose varchar(20) not null,
    code_hash varchar(64) not null,
    created_at timestamp(6) with time zone not null,
    expires_at timestamp(6) with time zone not null,
    attempts integer not null default 0,
    used_at timestamp(6) with time zone,
    constraint chk_email_code_purpose check (purpose in ('VERIFY_EMAIL'))
);
create index idx_email_code_owner_purpose on email_code (owner_id, purpose);
```

Don't edit existing migrations. CI's `PostgresMigrationTest` picks up V24
automatically.

        @DefaultValue("5") int maxAttempts,
        @DefaultValue("5") int maxSendsPerEmail,

### `mail/EmailCodeMailer.java`, `mail/SmtpEmailCodeMailer.java` and `mail/LoggingEmailCodeMailer.java` (new)

  On failure, log a WARN with the class name only, never the address or

  configured"`. A production log must never contain a code.
- **`MailConfig`:** add the `emailCodeMailer` bean with the same host
  rule as the reset mailer.

### `service/EmailCodeService.java` (new)

This is the shared code logic, which two-factor reuses.

- **Constructor:** `EmailCodeRepository`, `EmailCodeMailer`,
  `AttemptLimiter`, `SecurityLimitsProperties`, `Clock`, and
  `@Value("${flexbuddy.security.remember-me-key}") String secret`. The
  secret keys the hash.
- **`SendResult send(AppUser user, EmailCodePurpose purpose, String ip)`:**
  1. If `CODE_IP`/`ip` or `CODE_EMAIL`/the email key is locked, return
     `SendResult.LIMITED`.
  2. Otherwise record both, call
     `markUnusedAsUsed(owner, purpose, now)`, generate
     `String.format("%06d", random.nextInt(1_000_000))` from a
     `SecureRandom`, and save
     `codeHash = hex(HmacSHA256(secret, ownerId + ":" + purpose + ":" + code))`
     with `expiresAt = now + validFor`.
  3. Call `mailer.sendCode(...)` and return `SendResult.SENT`.

  A 6-digit code has only a million values, so a plain SHA-256 could be
  reversed from a leaked database in seconds. The key prevents that.
- **`CheckResult check(AppUser user, EmailCodePurpose purpose, String entered)`:**
  1. Strip spaces from `entered`. If it isn't exactly 6 digits, return
     `WRONG` without counting.
  2. Load the latest unused code. If there's none, or it has expired,
     return `EXPIRED`.
  3. If `attempts >= maxAttempts`, return `TOO_MANY`.
  4. Compare the hashes with `MessageDigest.isEqual`.
     - **On a match:** set `usedAt`, then return `OK`.
     - **Otherwise:** increment `attempts`, then return `WRONG`, or
       `TOO_MANY` if this was the last allowed try.
- **`@Scheduled(cron = "0 50 4 * * *") purgeExpired()`:** deletes codes
  that expired more than a day ago.
- The result enums are nested in this service.

### `service/EmailVerificationService.java` (new)

- **`AppUser startVerification(AppUser user, String ip)`:** calls
  `codes.send(user, VERIFY_EMAIL, ip)` and returns the user. The
  `SendResult` is passed back so the page can show "Too many codes
  requested. Try again in an hour."
- **`CheckResult verify(Long userId, String code)`:** on `OK`, sets
  `emailVerified = true` and saves.
- **`@Scheduled(cron = "0 55 4 * * *") purgeAbandoned()`:** deletes
  accounts where `emailVerified = false` and
  `createdAt < now - 24h`, using
  `AccountService.deleteAccountData(Long ownerId)`. That's a new
  package-private method split out of `deleteAccount`'s cleanup lines,
  so the cascade order stays in one place. These accounts can't have
  data, but the shared path keeps it safe.

### `service/AccountService.java`

- **`register(...)`:** if an account exists for the email with
  `emailVerified == false`, update its `displayName` and `passwordHash`
  and return it, so the address is reclaimed. Otherwise create it as now
  and set `user.setEmailVerified(false)` before saving.
- **`emailIsRegistered(email)`:** return true only for **verified**
  accounts. Add a repository method
  `existsByEmailIgnoreCaseAndEmailVerifiedTrue`.
- **Deletion:** split out `deleteAccountData(Long ownerId)` as described
  above, and add the `emailCodeRepository` delete.

### `service/PasswordResetService.java`

In `resetPassword` (line 113), after setting the new hash, add
`user.setEmailVerified(true)`. The link proves the driver owns the
address.

### `security/VerifiedLoginSuccessHandler.java` (new)

Replaces `defaultSuccessUrl("/", true)`.

- Constructor: `AppUserRepository`, `EmailVerificationService`,
  `PersistentTokenBasedRememberMeServices` and
  `SecurityContextLogoutHandler`.
- `onAuthenticationSuccess(request, response, authentication)`:
  - Look up the user.
  - **Verified:** `response.sendRedirect("/")`, as now.
  - **Unverified:**

       `PENDING_REMEMBER` (whether `remember-me` was ticked).
    4. Call `startVerification(user, request.getRemoteAddr())`.
    5. Redirect to `/verify-email`.

### `controller/EmailVerificationController.java` (new)

- `static final String PENDING_USER = "flexbuddy.pendingVerificationUser"`
  and `PENDING_REMEMBER = "flexbuddy.pendingVerificationRemember"`.
- **`GET /verify-email`:** with no pending id in the session, redirect to
  `/login`. Otherwise render `verify-email` with a masked address:
  `a••••@gmail.com`, keeping the first character and the domain.
- **`POST /verify-email`** (field `code`), using `verify(...)`:
  - `OK`:
    1. `request.changeSessionId()`.
    2. Build a `UsernamePasswordAuthenticationToken.authenticated` from
       `userDetailsService.loadUserByUsername(email)`, set it on a new
       `SecurityContext`, and save it with the
       `HttpSessionSecurityContextRepository`.
    3. If `PENDING_REMEMBER` is set, call
       `rememberMeServices.loginSuccess(new RememberMeRequest(request), response, auth)`.
       That's a small `HttpServletRequestWrapper` whose
       `getParameter("remember-me")` returns `"true"`.
    4. Remove both session attributes and redirect to `/?welcome`.
  - `WRONG`: re-render with "That code isn't right. Check the email and
    try again."
  - `EXPIRED`: "That code has expired. Send a new one."
  - `TOO_MANY`: "Too many wrong tries. Send a new code."
- **`POST /verify-email/resend`:** look up the pending user and call
  `startVerification`.
  - Sent: redirect to `/verify-email?resent`.
  - `LIMITED`: re-render with "Too many codes requested. Try again in an
    hour."
- **`POST /verify-email/cancel`:** removes the pending attributes and
  redirects to `/register`. This is "Use a different email". Add it to
  `permitAll`.

## 5. Ripple list

- **Shared records:**
  - `AccountSettingsResponse`, `BackupShift`, `BackupSettings`,
    `AccountBackupFile` (v4), `BlockEvaluationResponse` and
    `ShiftResponse` are unchanged.
  - `SecurityLimitsProperties` gains a last component, `Codes`.
- **New account data:** `email_verified` is excluded from the backup (see
  section 2), and `email_code` is temporary. Both are removed on account
  deletion.
- **Sign-in limits:** a wrong password still counts as before. A correct
  password on an unverified account clears the failure count, through
  the existing success event, and then sends a code. Code sends are
  limited separately (`code-email` and `code-ip`).
- **Remember-me:** never issued to an unverified account. The success
  handler removes it in the same request.
- **Play app:** the sign-up form now records the display mode, so a
  driver who signs up in the Play app stays signed in after verifying,
  as they would when signing in.
- **Email deliverability:** the code is in the subject so it shows in the
  notification. Gmail's sending limit, about 500 a day, is far above
  `max-sends`.
- **Error alerts:** a failed send logs at WARN, so there's no alert
  storm.
- **Phone layout:**
  - `.code-input` is the standard 47px field;
  - the text buttons are 44px tall;
  - there's no page widening.
- **Dates:** expiry uses the server `Clock` and instants, and nothing is
  shown in local time.
- **Tests building `SecurityLimitsProperties` by hand** need the new
  argument.

## 8. Commit message

```
feat(auth): confirm a new account's email with a six digit code

Anyone could create an account with any address, including someone
else's, and reset emails for it would then go to the real owner. A
new sign-up now lands on a Check your email page, and the account is
only signed in once the six digit code emailed to it is entered. The
code works for fifteen minutes and five tries, sends are limited per
address and connection, and only a keyed hash of it is stored, so a
leaked database cannot be searched for codes.

An unverified account that signs in with the right password is sent
a new code instead of being let in, and is never given a remember-me
token. Abandoned sign-ups are deleted after a day, and signing up
again with an address that was never confirmed replaces the old
attempt, so nobody can hold an address they do not own. Existing
accounts are marked as verified, and resetting a password also
confirms the address. The codes table is shared so two-factor sign-in
can reuse it.
```
