# Plan: optional two-step sign-in with an authenticator app or an emailed code

Planned against `origin/main` at 5de206b. **Ship `plan/email-verification`
first.** This plan reuses its `email_code` table, `EmailCodeService`,
`EmailCodeMailer`, the `code-email` and `code-ip` limiter buckets, and
`VerifiedLoginSuccessHandler`, with its pending-session pattern.

Decided: drivers can choose **either** method.

## Where things stand (after `plan/email-verification`)

- A correct password signs the driver in, unless the email is
  unverified, in which case `VerifiedLoginSuccessHandler` sends a code
  first.
- "Keep me signed in" issues a 30-day remember-me token
  (`RotationTolerantRememberMeServices`), and the Play app ticks it
  automatically.
- Sign-in failures are limited per email (5 per 15 min) and per
  connection.
- There's no second step, so a reused or leaked password is enough to
  open an account full of earnings and tax data.

## 1. Goal and out-of-scope

**Goal:**
- In Account → Account & privacy, a **Two-step sign-in** card opens a
  page where the driver turns on one method:
  - **Authenticator app:** a QR code, plus a setup key and an "Open in
    authenticator app" link for setting up on the same phone. The driver
    confirms by typing one 6-digit code. Google Authenticator, Microsoft
    Authenticator, 1Password, iCloud Passwords and others all work.
  - **Email code:** a 6-digit code is emailed at each sign-in. The driver
    confirms by entering one code, which proves the mail arrives.
- **Recovery codes:** turning either method on shows 10 single-use codes
  once, with Copy and Download buttons.
- **Signing in:** with two-step on, a correct password leads to **Enter
  your code** instead of Home. The page accepts the app code, the
  emailed code or a recovery code.
- **Trusted devices:** "Keep me signed in" still works after the second
  step. Remember-me sign-ins on that device skip the second step for 30
  days. The Play app ticks it automatically, so drivers aren't asked
  every time they open it.
- **Turning it off, or making new recovery codes,** needs the current
  password and a current code.
- **Brute force:** wrong codes count as failed sign-ins in the existing
  per-email limit.
- **Storage:** app secrets are stored encrypted, recovery codes as
  hashes, and email codes as keyed hashes (from the earlier plan).

**Out of scope:**
- SMS.
- Passkeys and WebAuthn.
- Requiring two-step for everyone.
- A list of trusted devices beyond the existing "Sign out everywhere".
- Admin tools to switch it off. The support process is in open question
  1.
- How Google sign-in interacts with two-step, which is decided in
  `plan/google-sign-in`.

## 2. Data model and migration

New `src/main/resources/db/migration/V25__two_factor.sql`:

```sql
-- Optional two-step sign-in: the method, the authenticator secret (encrypted by the app) and the last time step used,
-- so one app code cannot be replayed.
alter table app_users add column two_factor_method varchar(10);
alter table app_users add column totp_secret varchar(255);
alter table app_users add column totp_last_step bigint;
alter table app_users add constraint chk_two_factor_method check (two_factor_method in ('APP', 'EMAIL'));

-- Single-use recovery codes, stored as SHA-256 hashes.
create table recovery_code (
    id bigint generated by default as identity primary key,
    owner_id bigint not null references app_users(id) on delete cascade,
    code_hash varchar(64) not null,
    created_at timestamp(6) with time zone not null,
    used_at timestamp(6) with time zone
);
create index idx_recovery_code_owner on recovery_code (owner_id);

-- Emailed codes can now also be sign-in codes.
alter table email_code drop constraint chk_email_code_purpose;
alter table email_code add constraint chk_email_code_purpose check (purpose in ('VERIFY_EMAIL', 'SIGN_IN'));
```

### `model/AppUser.java`

- `@Enumerated(EnumType.STRING) @Column(length = 10) private TwoFactorMethod twoFactorMethod;`.
  Null means off.
- `@Column(length = 255) private String totpSecret;`. Encrypted, never
  the raw secret.
- `private Long totpLastStep;`.

### New enums and entity

- **`model/TwoFactorMethod`:** `APP`, `EMAIL`.
- **`model/EmailCodePurpose`:** add `SIGN_IN`.
- **`model/RecoveryCode`:** mirrors `EmailCode`, with
  `@OnDelete(CASCADE)` on the owner, plus `codeHash`, `createdAt` and
  `usedAt`.
- **`repository/RecoveryCodeRepository`:**
  - `findAllByOwnerIdAndUsedAtIsNull`
  - `deleteAllByOwnerId`
  - `countByOwnerIdAndUsedAtIsNull`

### Backup, restore and deletion

- **Backup:** two-step settings, the secret and recovery codes are
  **excluded** from backups on purpose. A backup file must never carry a
  sign-in secret. The format stays version 4, and `BackupSettings` is
  unchanged. Restore doesn't touch two-step.
- **Deletion:** add `recoveryCodeRepository.deleteAllByOwnerId(ownerId)` to
  `AccountService.deleteAccountData` (from the earlier plan). The columns
  on `app_users` go with the row.

## 3. Backend files

This draws the QR code server-side as SVG. It's Apache-2.0, has no

### `security/Totp.java` (new; pure)

RFC 6238 with HMAC-SHA1, 30-second steps and 6 digits. That's what every
authenticator app defaults to.

- `static String code(byte[] key, long timeStep)`: dynamic truncation,
  then `%06d`.
- `static OptionalLong matchStep(byte[] key, String entered, long nowStep)`:
  accepts `nowStep - 1`, `nowStep` and `nowStep + 1`, for phone clock
  drift. Compare with `MessageDigest.isEqual` on the bytes, and return
  the step that matched.
- `static byte[] newSecret()`: 20 bytes from `SecureRandom`.
- `static String base32(byte[])` and `static byte[] fromBase32(String)`:
  RFC 4648 with no padding. About 30 lines; don't add a library for it.
- `static String otpauthUri(String base32Secret, String email)`:
  `otpauth://totp/FlexBuddy:{urlencoded email}?secret={s}&issuer=FlexBuddy&algorithm=SHA1&digits=6&period=30`.

### `security/TwoFactorSecretCipher.java` (new)

- Holds `Encryptors.delux(key, salt)` (AES-256-GCM, from
  `spring-security-crypto`, already on the classpath).
- `key` is `@Value("${flexbuddy.security.two-factor-key}")`. `salt` is a
  fixed hex constant in this class, which is fine because the key is
  secret.
- Provides `encrypt(String base32)` and `decrypt(String stored)`.

### `service/TwoFactorService.java` (new)

Depends on `AppUserRepository`, `RecoveryCodeRepository`,
`EmailCodeService`, `TwoFactorSecretCipher`, `PasswordEncoder`,
`AttemptLimiter` and `Clock`.

**Setup (secrets kept in the HTTP session until confirmed):**
- `AppSetup beginApp(AppUser user)`: a new secret. Returns the base32
  secret, the `otpauth` URI and the QR as an SVG string (zxing
  `QRCodeWriter`, error correction `M`, drawn as `<rect>` cells in one
  `<path>`).
- `List<String> confirmApp(AppUser user, String base32, String code)`:
  - If `Totp.matchStep` fails, throw `InvalidTwoFactorCodeException`.
  - Otherwise store `totpSecret = cipher.encrypt(base32)` and
    `twoFactorMethod = APP`, set `totpLastStep` to the matched step,
    and return `newRecoveryCodes(user)`.
- `void beginEmail(AppUser user, String ip)`: calls
  `emailCodes.send(user, SIGN_IN, ip)`.
- `List<String> confirmEmail(AppUser user, String code)`: on
  `emailCodes.check(...) == OK`, set `twoFactorMethod = EMAIL`, clear
  `totpSecret`, and return `newRecoveryCodes(user)`.

**Recovery codes:**
- `newRecoveryCodes(user)`:
  1. Delete the old codes.
  2. Create 10 codes, each 10 characters from
     `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, formatted `XXXXX-XXXXX`.
  3. Store `sha256(uppercase, without the dash)`.
  4. Return the plain codes **once**.

**Signing in:**
- `Result verifySignIn(AppUser user, String entered)`, where
  `entered` is trimmed and spaces and dashes removed:
  1. **Recovery code:** if it's 10 characters, check the unused codes by
     hash. On a match, set `usedAt` and return `OK_RECOVERY`.
  2. **APP:** `matchStep` against the decrypted secret.
     - If the step matched is `<= totpLastStep`, return `WRONG`
       (replay).
     - Otherwise save `totpLastStep` and return `OK`.
  3. **EMAIL:** `emailCodes.check(user, SIGN_IN, entered)`, mapped to
     `OK`, `WRONG` or `EXPIRED`.
  4. **Every `WRONG`** also calls
     `limiter.record(AttemptLimiter.LOGIN_EMAIL, emailKey(user.getEmail()))`,
     so 5 wrong codes lock sign-in for that address for 15 minutes,
     exactly like 5 wrong passwords.
- `void sendSignInEmail(AppUser user, String ip)`: for the EMAIL method,
  and for the "Send a new code" button.

**Turning off and making new codes:**
- `void disable(AppUser user, String password, String code)`: requires
  `passwordEncoder.matches` and `verifySignIn(...)` OK. It then clears
  the method, secret and last step, and deletes the recovery codes.
- `List<String> regenerateRecoveryCodes(AppUser user, String code)`:
  requires `verifySignIn` OK.

### `security/SignInCompleter.java` (new; refactor)

Move the "sign this user in now" steps out of
`EmailVerificationController` (from the earlier plan) into one bean, so
both controllers share them:
1. `changeSessionId`.
2. Build the authenticated token from `userDetailsService`.
3. Save it with `HttpSessionSecurityContextRepository`.
4. If remember was requested, call
   `rememberMeServices.loginSuccess(new RememberMeRequest(request), …)`.

`EmailVerificationController` then calls `signInCompleter.complete(request, response, user, remember)`.

### `security/VerifiedLoginSuccessHandler.java` (extend)

After the unverified check, add:

- If `user.getTwoFactorMethod() != null`:
  1. Remove the remember-me token and the authentication, exactly as for
     unverified accounts.
  2. Store `TwoFactorController.PENDING_USER`, `PENDING_REMEMBER` and
     `PENDING_SINCE` (the instant) in the session.
  3. For the EMAIL method, call `sendSignInEmail(user, ip)`.
  4. Redirect to `/sign-in/code`.
- **Remember-me sign-ins don't pass through this handler.** Form login
  calls it; remember-me auto-login doesn't. That's what makes a trusted
  device skip the second step.

### `controller/TwoFactorController.java` (new)

**Signing in** (`permitAll`, CSRF-protected):
- **`GET /sign-in/code`:**
  - With no pending user, or `PENDING_SINCE` older than 10 minutes,
    clear and redirect to `/login?expired`.
  - Otherwise render `sign-in-code`, with:
    - `method`, and for EMAIL the masked address;
    - `remaining`, the number of recovery codes, without showing them.
- **`POST /sign-in/code`** (field `code`), using `verifySignIn`:
  - `OK` or `OK_RECOVERY`: `signInCompleter.complete(...)` and redirect
    to `/`. For `OK_RECOVERY`, redirect to `/?recovery-used` instead.
    Home shows a toast: "You used a recovery code. N left. Make new ones
    in Account."
  - `WRONG`: re-render with "That code isn't right." If the per-email
    limit is now locked, clear the pending session and redirect to
    `/login?locked`.
  - `EXPIRED` (email): "That code has expired. Send a new one."
- **`POST /sign-in/code/resend`:** EMAIL method only; sends a new code.
- **`POST /sign-in/code/cancel`:** clears the pending session and goes
  to `/login`.

**Settings** (signed in). No security change is needed:
`anyRequest().authenticated()` already covers `/account/two-factor/**`.
- **`GET /account/two-factor`:** renders `account-two-factor` with
  the current state (off, app or email) and the number of unused
  recovery codes.
- **App setup:**
  - `POST /account/two-factor/app`: `beginApp`. The secret is kept in
    the session under `SETUP_SECRET`. The page re-renders with the QR
    SVG, the setup key grouped in fours, the "Open in authenticator
    app" `otpauth:` link, and the confirm form.
  - `POST /account/two-factor/app/confirm`: `confirmApp`, using the
    session secret. On success, remove it and render the page with the
    recovery codes.
- **Email setup:**
  - `POST /account/two-factor/email`: `beginEmail`, then the page with
    a code form.
  - `POST /account/two-factor/email/confirm`: `confirmEmail`, then the
    recovery codes.
- **`POST /account/two-factor/recovery-codes`** (field `code`):
  `regenerateRecoveryCodes`, then show the new codes.
- **`POST /account/two-factor/disable`** (fields `password` and `code`):
  `disable`, then redirect to `/account/two-factor?off`.
- **Errors** re-render the page with a message. Nothing returns JSON;
  this is a server-rendered page like the reset pages.

## 5. Ripple list

- **Shared records:** none of `AccountSettingsResponse`, `BackupShift`,
  `BackupSettings`, `AccountBackupFile` (v4), `BlockEvaluationResponse`
  or `ShiftResponse` changes.
- **New account data:** the method, encrypted secret and last step on
  `app_users`, plus the `recovery_code` table.
  - **Backup and restore:** excluded on purpose. A restore doesn't turn
    two-step on or off.
  - **Deletion:** handled by `deleteAccountData` and the cascade.
- **Remember-me:** a device with a valid remember-me cookie skips the
  second step until it expires (30 days) or "Sign out everywhere" is
  used. That's the trusted-device behaviour, and it means Play app
  drivers aren't asked every launch.
- **Password reset:** doesn't turn two-step off. After a reset, the next
  sign-in still asks for the code. Reset already signs out remember-me
  devices.
- **Sign-in limits:** wrong codes share the 5-per-15-minutes per-email
  limit with wrong passwords.
- **Key rotation:** changing `FLEXBUDDY_TWO_FACTOR_KEY` makes every app
  secret unreadable. The comment in `application.properties` says never
  to change it.
- **The service worker** never caches `/account/two-factor`.
- **Phone layout:**
  - the QR box is 216px wide, which fits 375px with the card padding;
  - the recovery grid drops to one column under 380px;
  - the setup key wraps;
  - every button is 44px tall;
  - there's no page widening.
- **Dates:** the recovery-codes file date is the device's local date.
  Code expiry uses server instants.

## 6. Tests to add

**`security/TotpTest`:**
- With the RFC 6238 SHA-1 key `"12345678901234567890"` (ASCII):
  - `code(key, 59 / 30)` is `"287082"`;
  - `code(key, 1111111109 / 30)` is `"081804"`;
  - `code(key, 1234567890 / 30)` is `"005924"`;
  - `code(key, 2000000000 / 30)` is `"279037"`.

  These are the last 6 digits of the RFC's own vectors; I checked them
  with a standalone computation.
- `matchStep` accepts the previous, current and next step, rejects two
  steps away, and rejects `"12345"` and `"abcdef"`.
- `base32` round-trips 20 random bytes, and `fromBase32` ignores spaces
  and lowercase.
- `otpauthUri` URL-encodes `a+b@example.com`.

**`security/TwoFactorSecretCipherTest`:** an encrypt–decrypt round trip.
Two encryptions of the same secret differ (random IV), and the encrypted
value doesn't contain the base32 secret.

**`service/TwoFactorServiceTest`** (with `MutableClock`):
- `confirmApp` with the right code enables APP, stores an encrypted
  secret and returns 10 codes in `XXXXX-XXXXX` format.
- `verifySignIn`:
  - accepts the current code once, and returns `WRONG` for the same code
    again (replay);
  - accepts the next step's code.
- A recovery code works once. `"abcde-fghjk"` in lowercase matches its
  uppercase original, and the second use returns `WRONG`.
- 5 wrong codes lock `login-email` for that address.
- `disable` with a wrong password throws and changes nothing. With the
  right password and code, it clears everything and deletes the codes.
- The EMAIL method: `beginEmail` sends a `SIGN_IN` code, and
  `confirmEmail` with it enables EMAIL.

**`TwoFactorIntegrationTest`** (new; `@SpringBootTest`, MockMvc, a
`@Primary` capturing `EmailCodeMailer`, and a fixed clock so the test
can compute TOTP codes):
- **No two-step:** a user without it signs in straight to `/`, which
  pins that nothing changed for them.
- **APP user:** the password redirects to `/sign-in/code` with no
  remember-me cookie, and `GET /` redirects to `/login`. The right TOTP
  code redirects to `/`, and `GET /` returns 200.
- **APP user with "remember-me":** after the code, the remember-me cookie
  is set. A fresh session with only that cookie reaches `/` with no code
  asked for.
- **EMAIL user:** the password sends a `SIGN_IN` code, and that code
  signs them in.
- **Pending expiry:** a pending session older than 10 minutes redirects
  to `/login?expired`.
- **Wrong codes:** 5 wrong codes redirect to `/login?locked`.
- **Recovery code:** signs in and redirects to `/?recovery-used`.
- **Settings:** `POST /account/two-factor/app` then `/confirm` with a
  valid code shows 10 recovery codes. `GET /account/two-factor`
  afterwards shows "on" and never shows a code.

**`AccountDeletionJpaTest`:** an account with recovery codes deletes
cleanly.

**`StaticAssetsTest`:** passes, with `two-factor.js` precached.

**`src/test/js/two-factor.test.js`:**
`recoveryFileText(['AAAAA-BBBBB'], '2026-10-10')` contains the code and

**`PostgresMigrationTest`:** add `RecoveryCode` to the validated entities.

## 8. Commit message

```
feat(auth): add optional two-step sign-in by app or emailed code

A leaked or reused password was enough to open an account full of
earnings and tax records. Drivers can now turn on a second step in
Account and choose how to receive it. An authenticator app is set up
by scanning a QR code, by opening the setup link on the same phone or
by typing the key, and is confirmed with one code. Emailed codes
reuse the sign-up confirmation codes. Either way the driver gets ten
single-use recovery codes, shown once with copy and download.

After a correct password the driver enters the code before anything
else loads. A device kept signed in skips the step until its 30 day
token ends, so the Play app does not ask on every launch. Wrong codes
count toward the existing sign-in lock, an app code cannot be used
twice, app secrets are encrypted with a key held only in the
environment, and none of it is ever written to a backup. Turning it
off or making new recovery codes needs the password and a code.
```

## 9. Open questions

1. ~~Lost phone, lost email, no recovery codes?~~ **Decided:** support
   by email to `flexbuddysupport@gmail.com`. The operator clears
   `two_factor_method`, `totp_secret` and `totp_last_step` by hand once
   satisfied, and deletes the account's `recovery_code` rows. There's no
   admin page.
2. **The QR library.** This plan adds `com.google.zxing:core` 3.5.4 (about
   550 KB) to draw the QR server-side. The alternative is a self-hosted
   JS QR library. Server-side keeps the secret off any third-party
   script, so I recommend zxing.
