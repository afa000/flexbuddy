# Plan 15: Standing tracker

Planned against `origin/main` at `52da539` (latest migration V17, so this adds **V18**).
It follows the payout-deposit feature (`bfbecaf`) almost line for line. That feature is the
closest existing pattern: an owner-scoped row per date, with a note, carried in backups,
restored add-only, and removed on account deletion.

## 1. Goal and scope

Let a driver log their Amazon Flex standing (Fantastic, Great, Fair, At Risk) by hand, and
see it over the last 90 days next to their forfeits, late forfeits and cancellations. That
way, what changed after a late forfeit is visible in one place.

- **Manual only.** One entry per day: `(date, level, note)`. Logging a day again replaces
  its entry. The **current** standing is the entry with the latest date, even when that date
  falls outside the window.
- **FlexBuddy never infers or predicts standing.** The card says so in one line.
- **Where it shows:**
  - The dashboard's *Forfeits this month* tile gains a current-standing pill and a
    "Log standing" link.
  - The Schedule screen gains a *Standing* card: a step timeline, event markers, the entry
    form and the entry list.
- **Acceptance:**
  - Log Great on Aug 1, record a late forfeit on Sep 8, then log Fair on Sep 10. The timeline
    shows the late-forfeit marker on Sep 8, left of the step down on Sep 10, and the pill
    reads *Fair*.
  - Deleting the Sep 10 entry makes the pill read *Great* again.

### Changes from the draft

- **The API is keyed by date, not id:** `PUT /standing/{date}` and `DELETE /standing/{date}`.
  This matches `/payouts/{payoutDate}` and makes "one entry per day, logging again
  replaces it" the natural behaviour. There's no separate POST.
- **The backup format stays at version 4.** Tax payments (V16) and payouts (V17) were both
  added as new lists without a version bump. A missing list deserialises to empty, so older
  files restore unchanged. Decided: keep version 4.
- **The current standing is not added to `ShiftStatisticsResponse` or
  `AccountSettingsResponse`.** The tile reads it from `GET /standing`, so no shared record
  changes.

### Out of scope

- Reading standing from a screenshot. OCR would need samples of Amazon's standing screen.
- Reminders to log standing.
- A "Log standing" action on the forfeit toast. Decided: not wanted.
- Any score or sub-metric beyond the four levels (open question 3).
- The account page.

## 2. Data model and migration

**New file `src/main/resources/db/migration/V18__standing.sql`.** Don't edit any existing
migration.

```sql
create table standing_entry (
    id bigint generated by default as identity primary key,
    owner_id bigint not null references app_users(id) on delete cascade,
    recorded_on date not null,
    level varchar(16) not null,
    note varchar(255),
    created_at timestamp(6) with time zone not null,
    updated_at timestamp(6) with time zone not null,
    constraint uk_standing_entry_owner_date unique (owner_id, recorded_on),
    constraint chk_standing_entry_level check (level in ('FANTASTIC', 'GREAT', 'FAIR', 'AT_RISK'))
);
```

The unique constraint also serves `(owner_id, recorded_on)` lookups, so no extra index is
needed.

**New files in `model/`:**

- `StandingLevel.java`: enum `FANTASTIC, GREAT, FAIR, AT_RISK`, in best-to-worst order.
- `StandingEntry.java`, a copy of `PayoutDeposit`'s shape:
  - `@Table(name = "standing_entry", uniqueConstraints = @UniqueConstraint(name = "uk_standing_entry_owner_date", columnNames = {"owner_id", "recorded_on"}))`
  - Lombok `@Getter @Setter @NoArgsConstructor`.
  - Fields: `id`; `owner` (`@ManyToOne(fetch = LAZY, optional = false)`);
    `LocalDate recordedOn`; `@Enumerated(EnumType.STRING) @Column(nullable = false, length = 16) StandingLevel level`;
    `@Column(length = 255) String note`; `Instant createdAt` (`updatable = false`);
    `Instant updatedAt`.

The H2 test profile builds the schema from the entities with Flyway off, so the entity's
`@UniqueConstraint` is what enforces one entry per day in tests.

## 3. Backend

### New repository: `repository/StandingEntryRepository.java`

```java
List<StandingEntry> findByOwnerEmailIgnoreCaseAndRecordedOnBetweenOrderByRecordedOnAsc(String email, LocalDate from, LocalDate to);
Optional<StandingEntry> findFirstByOwnerEmailIgnoreCaseAndRecordedOnBeforeOrderByRecordedOnDesc(String email, LocalDate before);
Optional<StandingEntry> findFirstByOwnerEmailIgnoreCaseOrderByRecordedOnDesc(String email);
Optional<StandingEntry> findByOwnerEmailIgnoreCaseAndRecordedOn(String email, LocalDate recordedOn);
List<StandingEntry> findByOwnerEmailIgnoreCaseOrderByRecordedOnAsc(String email);   // backup and restore
long deleteAllByOwnerId(Long ownerId);                                              // account deletion
```

### `repository/ShiftRepository.java`: one derived query for the events

```java
List<Shift> findByOwnerEmailIgnoreCaseAndStatusInAndDateBetweenOrderByDateAscStartTimeAsc(
        String email, Collection<ShiftStatus> statuses, LocalDate from, LocalDate to);
```

`Shift` has `@SQLRestriction("deleted_at is null")`, so shifts in the trash are left out
automatically.

### New DTOs in `dto/`

All are records, and none is shared with existing code.

| Record | Fields and notes |
|---|---|
| `StandingEntryRequest` | `@NotNull StandingLevel level, @Size(max = 255) String note`. A missing or unknown level returns 400. |
| `StandingEntryResponse` | `LocalDate recordedOn, StandingLevel level, String note` |
| `StandingEventKind` | enum `FORFEITED, LATE_FORFEIT, CANCELLED` |
| `StandingEventResponse` | `LocalDate date, LocalTime startTime, String station, StandingEventKind kind` |
| `StandingResponse` | `LocalDate from, LocalDate to, StandingEntryResponse current, List<StandingEntryResponse> entries, List<StandingEventResponse> events`. `current` may be null. `entries` and `events` are never null (compact constructor `List.copyOf`). |
| `BackupStanding` | `LocalDate recordedOn, String level, String note`, `implements Serializable`. The level is a string, as `BackupPayout` keeps its amount as a string, so a bad value is skipped on restore instead of failing the whole file. |

### New exception: `exception/InvalidStandingException.java`

It extends `RuntimeException`. In `GlobalExceptionHandler`, add a handler that returns 400
with the message body, next to `InvalidPayoutException`.

### New service: `service/StandingService.java`

It takes `StandingEntryRepository`, `ShiftRepository`, `AppUserRepository`,
`UserTimeService` and `Clock` in its constructor.

**`StandingResponse window(String email, int days)`**

- If `days` is outside 7–365, throw `InvalidStandingException("Choose between 7 and 365 days.")`.
- Set `to = userTime.today(email)`, which uses the account's time zone, and
  `from = to.minusDays(days - 1)`.
- `entries` is the entry in force at `from` (the latest one before `from`, if any), followed
  by the entries in `[from, to]`. The carried-in entry keeps its real `recordedOn`, so the
  client draws the first step from the left edge.
- `current` is `findFirst…OrderByRecordedOnDesc`. That is the latest entry overall, so a
  future-dated entry can't exist (see below) and an old one still counts.
- `events` come from the new `ShiftRepository` query with `{FORFEITED, CANCELLED}` over
  `[from, to]`. FORFEITED with `isLateForfeit()` maps to `LATE_FORFEIT`, FORFEITED otherwise
  to `FORFEITED`, and CANCELLED to `CANCELLED`.

**`void log(String email, LocalDate recordedOn, StandingEntryRequest request)`**,
`@Transactional`:

- If `recordedOn.isAfter(userTime.today(email))`, throw
  `InvalidStandingException("Standing can be logged for today or an earlier day.")`.
- Otherwise find or create the entry, the same way `PayoutService.record` does. Set the level
  and the note (trimmed, and blank becomes null) and `updatedAt = Instant.now(clock)`.
  `createdAt` is set only on create.

**`void remove(String email, LocalDate recordedOn)`**, `@Transactional`: delete the entry if
there is one. A day with no entry is not an error.

### New controller: `controller/StandingController.java`

`@RestController @RequestMapping("/standing")`, modelled on `PayoutController`:

- `GET /standing?days=90` (`@RequestParam(defaultValue = "90") int days`) returns
  `StandingResponse`.
- `PUT /standing/{recordedOn}` (`@DateTimeFormat(iso = DATE)`, `@Valid @RequestBody StandingEntryRequest`)
  returns 204.
- `DELETE /standing/{recordedOn}` returns 204.

Security needs no change. Everything outside the public paths already requires sign-in, and
CSRF applies to PUT and DELETE, as it does for `/payouts`.

### Backup, restore and account deletion (the recurring rework item)

- **`dto/AccountBackupFile.java`**:
  - Add a 12th component, `List<BackupStanding> standing`, after `payouts`. The compact
    constructor defaults it with `standing = standing == null ? List.of() : List.copyOf(standing);`.
  - Add a compatibility constructor, "Backups made before standing was recorded", taking the
    current 11 components and passing `List.of()`.
  - Update the two older compatibility constructors (10 and 9 components) to pass one more
    `List.of()`.
  - Leave the 7-component constructor unchanged: it delegates to the 9-component one.
  - Jackson uses the canonical constructor, so a file without `standing` restores with an
    empty list.
- **`service/AccountBackupService.java`**: inject `StandingEntryRepository`, which changes
  the constructor. In `create`, pass the canonical 12th argument:
  `standingEntryRepository.findByOwnerEmailIgnoreCaseOrderByRecordedOnAsc(email)` mapped to
  `new BackupStanding(e.getRecordedOn(), e.getLevel().name(), e.getNote())`. Keep the format
  version at `4`.
- **`service/AccountRestoreService.java`**: inject `StandingEntryRepository`, which changes
  the constructor. Add `restoreStanding(file, owner)`, called right after
  `restorePayouts(file, owner)` and modelled on it:
  - It runs in both MERGE and REPLACE modes, and only adds entries for days that have none.
  - An entry already on the account is kept as it is.
  - Skip any entry with a null date, a date after the account's today, or a level that
    `StandingLevel.valueOf` rejects (catch `IllegalArgumentException` and `NullPointerException`).
  - Trim the note and cut it to 255 characters, as for payouts.
  - Set `createdAt` and `updatedAt` from `clock`, then `saveAll`.

  `RestorePreviewResponse` doesn't change. It doesn't count payouts or tax payments either.
- **`service/AccountService.java`**: inject `StandingEntryRepository`, which changes the
  constructor. In `deleteAccount`, call `standingEntryRepository.deleteAllByOwnerId(ownerId)`
  right after `payoutDepositRepository.deleteAllByOwnerId(ownerId)`. The foreign key's
  `on delete cascade` is a second safety net, not the mechanism.

### New file `static/js/standing.js`

An IIFE exposing `window.flexbuddyStanding = {load, focusForm}`. It uses app.js helpers at
call time (`apiFetch`, `csrfHeaders`, `showToast`, `formatDate`, `toIsoDate`,
`escapeHtml`, `showScheduleScreen`), as `payouts.js` does.

**Loading**

- `load()` fetches `GET /standing?days=90` once, keeps the response, and then:
  - Sets the tile pill: text and `data-level` from `current`, hidden when `current` is null.
  - Sets the tile link: "Log standing" when `current` is null, otherwise "Update standing".
  - If the Schedule screen is visible, renders the card.
- Call `window.flexbuddyStanding?.load()` from `loadDashboard()` in `app.js`, next to
  `window.flexbuddyFinish?.loadMissing()`, so forfeits recorded elsewhere refresh it. Also
  call it from the Schedule `show()` path: add one line in `showScheduleScreen` after
  `window.flexbuddySchedule.show()`.

**Tile link.** `#standingLink` calls `showScheduleScreen(false)`, then
`standingPanel.scrollIntoView({block: 'start'})`, then focuses the first level button.

**Form**

- The date defaults to `toIsoDate(new Date())`, the device's local date. Never use
  `toISOString()` here.
- The input has `max` set to the same value. The server still rejects a future day in the
  account's time zone, and its message is shown in `#standingError`.
- Level buttons behave like a single-choice group. The chosen one gets `is-active` and
  `aria-pressed="true"`, and the others are cleared.
- Save is disabled until a level is chosen. So the shortest path is two taps: a level, then
  Log standing.
- If the chosen date already has an entry in the loaded data, `#standingReplaceHint` reads
  "Replaces Fair logged for Sep 10."
- Submit sends `PUT /standing/{date}` with `{level, note}`, then reloads with `load()` and
  shows the toast "Standing logged / Fair from Sep 10."

**Entry list** (`#standingList`)

- The window's entries and events merged, newest first:
  - An entry row shows the date, the level pill, the note, **Edit** (loads it into the form)
    and **Delete**.
  - An event row shows the date, station, start time and a label: *Late forfeit*, *Forfeit*
    or *Cancelled by Amazon*.
- **Delete** sends `DELETE /standing/{date}`, reloads, and shows the toast "Standing removed"
  with an **Undo** action for 8 seconds. Undo re-sends a PUT with the removed level and note.
- Edit and Delete get `data-online-only`. Because rows are rendered after load, also check
  `window.flexbuddyPwa?.isOffline()` when rendering, as `finish.js` does.
- Empty state: "No standing logged yet. Log it from the Flex app when it changes."

### `static/js/charts.js`: add `renderStanding(container, data)`

Export it from `window.flexbuddyCharts`.

**Layout**

- An SVG with `viewBox="0 0 360 170"`, `width: 100%`, `height: auto`, `role="img"` and an
  `aria-label` summary. Example: "Standing over the last 90 days: Great from Aug 1, Fair
  from Sep 10. 1 late forfeit, 1 forfeit, 0 cancellations."
- A left gutter of 62 units for the level labels. Rows at y = 22, 50, 78 and 106 for
  Fantastic, Great, Fair and At Risk, with light gridlines.
- The x axis maps `from` to `to` linearly, one column per day. First-of-month ticks are
  labelled `Sep` under the axis at y = 162.

**Steps**

- One horizontal segment per entry, from `max(recordedOn, from)` to the next entry's date,
  or to `to` for the last one.
- Vertical joins between segments. Each segment is coloured by level.
- Before the first entry nothing is drawn: no level is known there.

**Event markers** on a band at y = 134:

- Late forfeit: a filled triangle in `--error`.
- Forfeit: an outlined triangle in `--warning`.
- Cancelled: a small outlined circle in `--muted`.
- Events on the same day stack 8 units apart.
- Each marker has a `<title>` like "Late forfeit · VEA7 · Sep 8". Touch screens don't show
  `<title>`, which is why the list below carries the same details as text.

The SVG scales to its container, so it never widens the page. The container
`.standing-chart` gets `min-width: 0`.

## 8. Suggested commit message

```
feat(schedule): track your Flex standing next to forfeits

Drivers can now log their Flex standing, from Fantastic to At Risk,
whenever the Flex app shows a change. The Schedule screen has a
Standing card with the last 90 days drawn as steps, forfeits, late
forfeits and cancellations marked on the same timeline, and a short
form where choosing a level and tapping Log standing is enough. The
Forfeits this month tile shows the current standing and links straight
to the form.

Standing is only ever what the driver logged. FlexBuddy never guesses
it, and the card says so. One entry is kept per day, so logging a day
again replaces it, and the current standing is the latest entry even
when it is older than the window. A day after today in the account's
time zone cannot be logged, and a removed entry can be put back with
Undo.

Logged standing is carried in backups, a restore adds entries for days
that have none yet in either mode, and deleting the account removes
them. The backup format stays at version 4, as older files simply have
no standing to add.
```

## 9. Decisions and open questions

### Decided

- **The card lives on the Schedule screen**, with the dashboard tile's link jumping to it,
  as planned in section 4.
- **The forfeit toast gets no "Log standing" prompt.** The tile link is the only way in
  besides the Schedule screen.
- **The backup format stays at version 4.** `AccountRestoreService`'s `> 4` check and its
  tests don't change.

### Still open

1. **Window.** A fixed 90 days, or a 30 / 90 / 180 switch? The API already takes `days`, so
   a switch would be frontend only. The plan ships a fixed 90 days unless you say otherwise.
2. **How far back.** Any past date can be logged, which is useful for back-filling from
   memory. Should there be a limit, such as one year? The plan ships with no limit.
3. **Levels.** Some regions show extra tiers, such as "Fantastic Plus", or sub-scores like
   reliability. Are the four levels all you want, or should the check constraint allow
   more? Adding a level later means a new migration to widen the check. The plan ships the
   four levels.
