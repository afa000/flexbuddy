# Plan 11: Receipt photos

Planned against `origin/main` at `eef0595` (latest migration V20, so this adds **V21**). It
replaces the draft `plans/receipt-photos-draft.md` that was on this branch.

## How the draft is split

The draft is three features, so it becomes three plans, and this file is the first:

| Plan | What it covers | Status |
|---|---|---|
| **11 (this plan)** | Attach, view, replace and delete a receipt photo on an expense, and download all photos as a zip | Planned here |
| **11b** | Backups that carry the photos and restore them | Follow-up, not written yet |
| **17** | Reading the amount off the receipt with OCR | Follow-up, not written yet |

## Where this plan differs from the draft, and why

1. **The photo is stored in the database (`bytea`), behind a `ReceiptStore` interface.** That
   was the draft's recommendation, and it holds up.
   - The web service's disk is ephemeral on Render (the `starter` plan in `render.yaml`).
   - Object storage would add a vendor account, keys and CORS for one feature.

   The draft's figures need correcting. The database is on Render's **paid `basic-256mb`**
   plan, not the free one, so check its storage size in the Render dashboard before
   shipping. The cap drops from 400 KB to **300 KB**. At that size, 300 receipts a year come
   to about 90 MB.
2. **Backups don't carry photos in this plan. A separate zip download does.**
   - The draft's "backup v3 with base64 photos" doesn't fit this app.
   - The JVM runs with default settings (`java -jar` in `docker-entrypoint.sh`), so its heap
     is about a quarter of the 512 MB instance, roughly 128 MB.
   - `AccountBackupService` builds the whole backup in memory and Jackson writes it in one
     go. 300 photos, encoded as base64, would be around 120 MB, which would run it out of
     memory.
   - So this plan adds **"Download receipt photos (.zip)"**, which streams one photo at a
     time. Restoring photos from a backup is plan 11b, which would use a zip backup format.
   - The backup format stays at **version 4**, and `BackupExpense` doesn't change.
3. **OCR amount reading moves to plan 17.** Receipt text is much noisier than app
   screenshots, and Tesseract uses a lot of the small instance's memory, so it deserves its
   own plan and measurements.
4. **The server re-encodes every upload to JPEG.** This strips all metadata, including any
   GPS location a phone camera may have embedded. The browser's resize already drops it, but
   the server can't rely on the browser.
5. **Play and privacy.** Your Play Data safety answers declare Photos as *processed
   ephemerally* (`android/play-app-content.md`), and the privacy policy says images are
   never stored. Both become untrue with this feature. Updating them is part of this plan
   (section 4 and step 12 of section 7), not an afterthought.
6. **Offline.** Since `eef0595`, an expense added offline is queued with no id yet, so a
   photo can't go with it. While offline, the photo button is disabled with a hint, and the
   photo can be added from the expense row once it syncs. Queueing photos is out of scope.

## 1. Goal and scope

**What the driver can do:**

- On the expense form, tap **Add receipt photo**. The phone's camera opens, or the gallery
  on desktop. A thumbnail appears.
- On save, the expense is created and then the photo uploads.
- Expense rows with a photo show a receipt icon. Tapping it opens a full-screen viewer that
  can be zoomed, with **Replace photo** and **Delete photo**.
- A row without a photo has **Add photo** in its actions.
- The account page's Data card shows **Receipt photos: 38 · 11.2 MB** and **Download
  receipt photos (.zip)**.
- Photos are shown only to their owner, over a signed-in request, and are never cached by
  the service worker.

**Which expenses:** any category can have one photo. The draft limited it to four
categories; one photo per expense of any kind is simpler and harmless.

### Out of scope

- Restoring photos from backups (11b).
- OCR (17).
- More than one photo per expense.
- PDFs.
- Photos on shifts.
- Queueing photos offline.
- Object storage. `ReceiptStore` leaves the door open for it later.

## 2. Data model and migration

**New file `V21__receipts.sql`.** Don't edit any existing migration.

```sql
create table receipt (
    id bigint generated by default as identity primary key,
    owner_id bigint not null references app_users(id) on delete cascade,
    expense_id bigint not null references expense(id) on delete cascade,
    content_type varchar(20) not null,
    size_bytes integer not null,
    width integer not null,
    height integer not null,
    data bytea not null,
    created_at timestamp(6) with time zone not null,
    constraint uk_receipt_expense unique (expense_id),
    constraint chk_receipt_size check (size_bytes > 0 and size_bytes <= 307200),
    constraint chk_receipt_content_type check (content_type = 'image/jpeg')
);
create index idx_receipt_owner on receipt (owner_id);
```

The unique constraint indexes `expense_id`, so no second index is needed for it.

### The cascade is the deletion mechanism, and the entity must declare it

Every expense delete is **native SQL** today:

- `ExpenseRepository.permanentlyDelete`
- the empty-trash `delete`
- `purgeDeletedBefore`, used by `ShiftPurgeJob`
- `deleteAllByOwnerIdIncludingTrash`, used by account deletion

Hibernate's cascades never run for native deletes, so the database's `on delete cascade` is
what removes a receipt. The H2 test schema is built **from the entities**, so the entity
must declare the cascade too, or those deletes fail with a foreign-key error in tests.

**`model/Receipt.java`:**

- `@Entity @Table(name = "receipt", uniqueConstraints = @UniqueConstraint(name = "uk_receipt_expense", columnNames = "expense_id"))`
- `@ManyToOne(fetch = LAZY, optional = false) @JoinColumn(name = "owner_id") @OnDelete(action = OnDeleteAction.CASCADE) AppUser owner`
- `@OneToOne(fetch = LAZY, optional = false) @JoinColumn(name = "expense_id") @OnDelete(action = OnDeleteAction.CASCADE) Expense expense`
- `String contentType`, `int sizeBytes`, `int width`, `int height`, `Instant createdAt`
- `@Column(nullable = false) byte[] data`

  Don't use `@Lob`: in Postgres it maps to `oid`, not `bytea`. `PostgresMigrationTest`
  checks that the mapping matches the migration.

`Expense` gets **no** field for the receipt. That keeps expense loading from ever pulling
photo bytes into memory.

Soft-deleting an expense keeps its receipt. Restoring the expense brings the photo back.
Purging or permanently deleting the expense removes the photo.

## 3. Backend

### New repository: `repository/ReceiptRepository.java`

```java
Optional<Receipt> findByExpenseIdAndOwnerEmailIgnoreCase(Long expenseId, String email);   // serving the image

@Query("select r.expense.id from Receipt r where r.owner.email = :email and r.expense.id in :ids")
Set<Long> expenseIdsWithReceipt(@Param("email") String email, @Param("ids") Collection<Long> ids);   // lists, no bytes

@Query("select count(r), coalesce(sum(r.sizeBytes), 0) from Receipt r where lower(r.owner.email) = lower(:email)")
Object[] usage(@Param("email") String email);   // wrap it in a small record in the service

@Query("select r.id from Receipt r where lower(r.owner.email) = lower(:email) order by r.expense.date, r.id")
List<Long> idsForOwner(@Param("email") String email);   // the zip streams one photo at a time

@Modifying @Query("delete from Receipt r where r.expense.id = :expenseId and r.owner.email = :email")
int deleteForExpense(…);
```

Make the email match in the first and last methods case-insensitive too. Use native SQL if
JPQL `lower` on the path gets awkward.

### `service/ReceiptStore.java` (interface) and `DatabaseReceiptStore` (the only implementation)

The interface exists so object storage could replace the database later without touching
the controllers.

```java
void put(String email, Long expenseId, StoredImage image);   // insert or replace
Optional<StoredImage> get(String email, Long expenseId);
boolean delete(String email, Long expenseId);
```

`StoredImage` is a record: `(byte[] data, String contentType, int width, int height)`.

### New service: `service/ReceiptService.java`

**`upload(String email, Long expenseId, MultipartFile file)`**, `@Transactional`:

1. The expense must belong to the caller **and not be deleted**, using
   `expenseRepository.findByIdAndOwnerEmailIgnoreCase`. It has `@SQLRestriction`, so trashed
   expenses aren't found. Otherwise throw `ExpenseNotFoundException`, which gives 404.
2. The content type must be `image/jpeg`, `image/png` or `image/webp`. The raw size must be
   at most **5 MB**, the existing multipart limit.
3. Decode with `ImageIO`, reusing the dimension-check approach in `ShiftImportService`:
   - read the size before decoding the pixels;
   - reject over 12,000 px on a side;
   - reject a file that isn't an image.

   **WebP:** `ImageIO` has no WebP reader. Either reject WebP with "Use a JPEG or PNG photo"
   or add a reader dependency. **Reject**, since the browser always sends JPEG after its
   resize (below).
4. **Normalise:**
   - Scale down so the long edge is at most **1600 px**. It's never scaled up.
   - Draw onto an RGB `BufferedImage`, which drops transparency.
   - Write it as JPEG at quality **0.8** through an `ImageWriter`. Writing a fresh image
     carries **no EXIF**, so no GPS, camera or time metadata is stored.
   - If the result is over **300 KB**, re-encode at 0.7, then at 0.6. If it's still over,
     reject with "This photo is too detailed to store. Try a closer photo of just the
     receipt."
5. `store.put(...)`. The response is `ReceiptInfo(expenseId, width, height, sizeBytes)`.

Keep the image at most 1600 px on a side while it's being processed. A 12 MP camera photo
decodes to about 48 MB, which the 128 MB heap can handle one at a time. The browser shrinks
it before upload anyway, so this path only matters for uploads that skip the browser.

**Other methods:**

- `get(email, expenseId)`: owner-checked, **trash included**, so a trashed expense's photo
  can still be viewed from Recently deleted. Use a query that doesn't depend on the expense
  entity's `@SQLRestriction`: go through `Receipt.owner`.
- `delete(email, expenseId)`: owner-checked. A missing photo is a 404.
- `usage(email)` returns `ReceiptUsage(count, bytes)`.
- `writeZip(email, OutputStream)`, `@Transactional(readOnly = true)`:
  - Stream a `ZipOutputStream` by looping over `idsForOwner`. Load **one** receipt at a time
    and `entityManager.detach` it after writing, so no more than one photo is ever in memory.
  - Entry names: `2026-09-29_fuel_45.20_expense-123.jpg`, using the expense date, the
    category in lower case, the amount at 2 decimals, and the expense id.
  - Use `ZipEntry.STORED`: JPEG doesn't compress further, and storing saves CPU.

### DTO change: `ExpenseResponse` (a record) gets `hasReceipt`

- **Append** `boolean hasReceipt` as the **11th and last** component.
- Add a 10-component compatibility constructor with the current signature, passing `false`.
  That keeps `ExpenseControllerTest`'s one call compiling unchanged.
- In `ExpenseService.toResponse`:
  - Single expense: one `existsBy…` check.
  - **Lists (`findAll`, trash, per-shift expenses):** collect the ids and call
    `expenseIdsWithReceipt` **once**, then pass the set into the mapping. Never query once
    per row.

### Controllers

New `controller/ReceiptController.java`, `@RestController`:

| Endpoint | Behaviour |
|---|---|
| `POST /expenses/{id}/receipt` | Multipart part `receipt`. Returns `ReceiptInfo`. Replaces an existing photo. |
| `GET /expenses/{id}/receipt` | Returns the bytes with `Content-Type: image/jpeg`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Content-Disposition: inline; filename="receipt-{id}.jpg"`. 404 if there is none or it isn't the caller's. |
| `DELETE /expenses/{id}/receipt` | 204 |
| `GET /expenses/receipts.zip` | Streams the zip. `Content-Disposition: attachment; filename="flexbuddy-receipts.zip"`, `Cache-Control: no-store`. |
| `GET /account/receipts/usage` | `{count, bytes}` |

Mapping order: `/expenses/receipts.zip` must not be taken as `/{id}`. The id is numeric, so
use `{id:\\d+}` on the receipt mappings.

Upload errors use a new `InvalidReceiptException`, which `GlobalExceptionHandler` maps to 400
with the message.

### Account deletion, backups and restore

- **Account deletion:** it already deletes the expenses (native SQL), and the database
  cascade removes their receipts. **Also add** `receiptRepository.deleteAllByOwnerId(ownerId)`
  in `AccountService.deleteAccount`, **before** the expense delete, as belt and braces. That
  follows the pattern of every other owned table, and keeps working even if the cascade is
  ever lost.
  - `AccountService` gets a constructor parameter, so **add a `@Mock` to
    `AccountServiceTest`**, which uses `@InjectMocks`.
- **Backup:** the format is unchanged, version 4, with no photos. The Data card says so
  next to the backup button: "Backups don't include receipt photos. Download them
  separately."
- **Restore:** a REPLACE restore soft-deletes the current expenses. Their receipts stay with
  them in the trash, and go when the trash is purged. Nothing else to do.

### Security and the service worker

- **Security:** no change. Every new path requires sign-in, and CSRF applies to POST and
  DELETE. The multipart POST sends the CSRF header from the page, as the import upload does.
- **`sw.js`:** `DATA_PATHS` has `/^\/expenses(\/|$)/`, which would **cache photos** in the
  data cache. Add these to `NETWORK_ONLY`:
  - `/^\/expenses\/\d+\/receipt$/`
  - `/^\/expenses\/receipts\.zip$/`
  - `/^\/account\/receipts\/usage$/`

  `NETWORK_ONLY` is checked before `DATA_PATHS`, so this is enough.

### New file `static/js/receipts.js`

An IIFE exposing
`window.flexbuddyReceipts = {pick, clearPick, pending, upload, openViewer, shrink}`. Add it to
`VERSIONED_ASSETS` in `sw.js` and to the page's script tags, before `app.js`.

**`shrink(file)`**, the browser-side resize:

1. `createImageBitmap(file, {imageOrientation: 'from-image'})`, so photos taken sideways
   come out upright.
2. Scale the long edge to at most 1600 px and draw onto a canvas.
3. `canvas.toBlob(blob => …, 'image/jpeg', 0.8)`. If the result is over 300 KB, retry at 0.7,
   then 0.6.

The re-encode strips EXIF in the browser too. Keep the math, meaning target size and
quality steps, in a pure `shrinkPlan(width, height)` that returns `{width, height}`, so it
can be tested with `node --test`.

**Choosing and attaching a photo:**

- `pick()` opens the input, then `shrink`s the file, shows the thumbnail through

    has a blob, `upload(expenseId, blob)` sends

  - **If the save was queued offline,** the button was already disabled, so there's nothing
    to upload. Also call `clearPick()` defensively.
  - `resetExpenseForm` also calls `clearPick()` and revokes the object URL.

    - The download opens as a zip with 2 JPEGs, named by date, category and amount.
11. **Deletion.**
    - Delete an expense with a photo: it's in Recently deleted, and its photo can still be
      viewed.
    - Delete it permanently: its row is gone from `receipt`, which you can check with psql,
      or rely on test 17.
    - Delete a throwaway account with photos: no `receipt` rows are left.
12. **Play Console.** Update Data safety as described in section 4, before or on the deploy
    day. The privacy page at `/privacy` shows the new Receipt photos section.

## 8. Suggested commit message

```
feat(expenses): attach a receipt photo to an expense

An expense can now carry a photo of its receipt. The expense form opens
the phone's camera, the photo is resized in the browser before it is
sent, and a receipt icon on the row opens it full screen with zoom,
where it can be replaced or deleted. A row without a photo can have one
added later, including an expense that was saved offline and has since
synced.

The server re-encodes every photo as a JPEG of at most 1600 pixels and
300 KB, which also removes any location or camera details the phone
added. Photos are kept in the database, shown only to their owner, and
never cached on the device. They go when the photo, the expense or the
account is deleted, and a Recently deleted expense keeps its photo
until it is purged.

Backups stay as they are; the account page downloads all receipt
photos as a zip instead and shows how much space they use. The privacy
policy and the Play data safety notes now say receipt photos are
stored.
```
